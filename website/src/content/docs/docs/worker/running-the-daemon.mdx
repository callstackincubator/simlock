The daemon is the background process that owns this machine's devices and leases. Every `simlock` command talks to it, and the first command that needs it starts it. You only manage it by hand to apply a config change, to start it at login, or to update Simlock.

## Start the daemon

```sh
simlock daemon start
```

```text
Daemon running
Console: http://127.0.0.1:4701/
```

The `Console:` line appears only when HTTP is on. If the daemon is already running, the command does nothing and prints the same lines.

You rarely need this command: any command that needs the daemon starts it and waits up to 20 seconds for it. The daemon keeps running after you close the terminal, but it does not come back after a reboot unless you [start it at login](#start-it-at-login).

## Restart it to apply a config change

The daemon reads `config.json` only when it starts. After `simlock config set`, restart it:

```sh
simlock daemon stop
simlock daemon start
```

If `daemon start` fails with `DAEMON_STOPPING`, the old daemon is still finishing work in progress, such as a device reset. Wait a few seconds and run it again.

## Stop the daemon

```sh
simlock daemon stop
```

```text
Daemon stopping
```

Stopping the daemon does not end leases. It shuts down every device that has no lease, and leaves leased devices running; the next daemon picks them up (see [What a restart keeps](#what-a-restart-keeps)).

The command returns at once, but the daemon may take a while to finish the work it has started. Commands sent in the meantime fail with `DAEMON_STOPPING`.

## Start it at login

On macOS and Linux, install the daemon as a service:

```sh
simlock daemon install
```

On macOS:

```text
Service installed: com.callstack.simlock.worker (launchd)
Daemon running
To start after a reboot, turn on automatic login for this user.
```

On Linux:

```text
Service installed: com.callstack.simlock.worker (systemd)
Daemon running
To start after a reboot without logging in, run: loginctl enable-linger <user>
```

The service starts the daemon when you log in, and starts it again 10 seconds after it crashes. If a daemon was already running, the command first stops it; leases are kept.

Before you rely on it, know what it needs:

- **macOS:** the service runs only while your user is logged in at the screen. For the machine to come back after a reboot, turn on automatic login for this user.
- **Linux:** without linger, logging out of your last session stops the daemon and its emulators. Run `loginctl enable-linger <user>` to keep them running. Simlock does not turn linger on for you.
- **Environment:** the service remembers `SIMLOCK_HOME`, `PATH`, `JAVA_HOME`, `DEVELOPER_DIR` and the Android SDK variables (such as `ANDROID_HOME`) as they are when you run `daemon install`.

Run `simlock daemon install` again after you change one of those variables, or after you move or upgrade Node or Simlock (for example with nvm or Homebrew).

`simlock daemon stop` still stops a daemon that runs as a service, and the service leaves it stopped until the next command.

To remove the service:

```sh
simlock daemon uninstall
```

This stops the daemon and removes the service. On Windows, `daemon install` and `daemon uninstall` are not available.

### When the service cannot run

If nobody is logged in at the screen (for example, you are connected over SSH), or the service points at a Node or Simlock that is gone, commands still work. They start the daemon without the service and say so:

```text
Service com.callstack.simlock.worker is not loaded; started the daemon without it.
```

On Linux, `daemon install` with no login session and no linger fails with `SERVICE_FAILED` (`Failed to connect to bus`) and installs nothing. Log in, or turn on linger, and run it again.

If the daemon does not come up through the service within 20 seconds, the command fails with `DAEMON_STARTUP_FAILED` and shows the log lines written since the start.

## Check whether it is running

```sh
simlock daemon status
```

This never starts the daemon. It prints `Daemon stopped`, or, when the daemon runs, the same report as `simlock status`:

```text
Daemon: running (worker)
```

`starting` means the daemon is still reading the machine's devices. Devices, leases and capacity appear once it finishes. [Monitoring](/simlock/docs/worker/monitoring) explains the rest of the report.

On macOS and Linux the last line shows the service:

| Line | What it means |
| --- | --- |
| `Service: not installed` | You have not run `simlock daemon install`. |
| `Service: installed (launchd, com.callstack.simlock.worker)` | The service is set up and working. |
| `Service: not loaded (...)` | Nobody is logged in at the screen, or there is no Linux user session. Commands start the daemon without the service. |
| `Service: broken (...): <path> is gone; run simlock daemon install` | The Node or Simlock the service starts has moved, for example after an nvm or Homebrew upgrade. Run `simlock daemon install` again. |

Add `--json` for a machine-readable answer, such as `{"status":"stopped"}`.

## Where files live

Everything the worker keeps is under `~/.simlock`, or the folder `SIMLOCK_HOME` names:

| Path | What it holds |
| --- | --- |
| `config.json` | Your settings. See [Configuration](/simlock/docs/worker/configuration). |
| `state.db` | Devices, leases, enrolled physical devices, what the warm pool learned, and HTTP tokens. |
| `history.db` | The event history and usage figures behind `simlock events` and `simlock stats`. |
| `daemon.log`, `daemon.log.1` | The daemon's log, and one older file. |
| `daemon.sock` | The socket the CLI and agents connect to. |
| `admin.token` | The secret the CLI uses to connect as an admin. |
| `devices/ios`, `devices/android` | The simulators and emulators Simlock made. These take the most space. See [Cleanup](/simlock/docs/worker/cleanup#where-devices-live). |

<Aside type="caution">
`~/.simlock/devices` can grow to tens of gigabytes. Do not delete folders in it by hand while the daemon runs. Use `simlock cleanup`, or [`simlock nuke`](/simlock/docs/worker/cleanup#reset-a-machine-with-nuke) to start over.
</Aside>

Anyone who can open `~/.simlock` can lease devices, so Simlock creates it readable by your user only. It does not change a folder that already exists. If other users can open it, the daemon log says so at each start, with the `chmod 700` command that fixes it.

A gateway on the same machine keeps its own files in `~/.simlock/gateway` and runs its own daemon. Add `--gateway` to reach it, for example `simlock --gateway daemon status`. See [Set up a gateway](/simlock/docs/gateway/setup).

You can run one worker per user on a machine. A second worker started from another `SIMLOCK_HOME` refuses to start and prints the command that stops the first one.

<Aside type="caution" title="Windows">
On Windows, the folder's permissions do not protect the daemon's connection, and another account on the same machine could intercept it. Run Simlock on Windows only on a machine that one user account uses.
</Aside>

## Read the daemon log

```sh
simlock daemon logs            # the last 100 lines
simlock daemon logs --follow   # then each new line, until Ctrl-C
```

[Monitoring](/simlock/docs/worker/monitoring#read-the-daemon-log) explains the log's format and how to make it more detailed.

## What a restart keeps

After a `daemon stop`, a crash or a reboot, the new daemon checks its records against the devices that really exist:

- **Idle devices are shut down** by a `daemon stop` or an update. They boot again when a lease or the warm pool needs them. A crash or a reboot leaves them as they were.
- **A lease whose device is still running is kept.** Its agent can go on renewing it. If its time ran out while no daemon was running, it expires when the daemon starts.
- **A lease whose device stopped running ends.** This is what happens after a reboot. The lease ends with reason `device-lost` (or as expired, if its time had run out).
- **A lease on a physical device is kept.** It ends as usual: when its time runs out or the device is unplugged.
- **A request still waiting in the queue fails** with `INTERNAL`: `The daemon restarted before this lease request settled; send it again with a new key`. The agent has to ask again.

## Update Simlock

`simlock update` installs the newest Simlock and restarts the daemon once the current leases have ended:

```sh
simlock update
```

```text
Updating simlock 0.3.0 → 0.4.0
Waiting for 2 leases to end. Ctrl-C stops following; simlock update --force stops waiting.
Installing simlock@0.4.0
Restarting the daemon
simlock 0.4.0 is running
```

While it waits, the daemon takes no new leases: new and queued requests fail with `DAEMON_UPDATING`. Leases already held renew and release as usual. `simlock status` shows `Updating to 0.4.0: waiting for 2 leases`.

- `--force` stops waiting and restarts now. Leases on running devices survive the restart. You can run it from another shell while an update waits.
- `--version 0.4.0` installs that exact version, older ones included.

If something goes wrong:

| What happens | Result |
| --- | --- |
| The install fails, for example npm cannot write its global folder. | The old daemon keeps running and takes leases again. `simlock status` shows `Last update failed (installing): <npm's message>`. |
| The new version does not start within two minutes. | Simlock puts the old version back and starts it. `simlock status` shows `Last update failed (restarting): …`. |
| `UPDATE_UNSUPPORTED_INSTALL` | Simlock was not installed with `npm i -g simlock` (for example, a source checkout or a pnpm global install). Nothing changes. Upgrade by hand. |
| `UPDATE_SHARED_INSTALL` | A worker and a gateway of the same user share one install, and the other one is running. Stop it, update, then start it again. |
| `PROTOCOL_VERSION_UNSUPPORTED` | The running daemon is too old to update itself. Upgrade by hand. |

Admins can also run the update over HTTP with `POST /v1/update`.

## Upgrade by hand

<Steps>

1. Stop the daemon:

   ```sh
   simlock daemon stop
   ```

   This works even when the daemon is a different version and refuses other commands with `PROTOCOL_VERSION_UNSUPPORTED`.

2. Install the new version:

   ```sh
   npm i -g simlock
   ```

3. Start the daemon and check the machine:

   ```sh
   simlock daemon start
   simlock doctor
   ```

</Steps>

Leases on running devices survive the upgrade.

### Upgrade from a version that used `state.json`

Older versions kept their state in `~/.simlock/state.json` and HTTP tokens in `~/.simlock/tokens.json`. The current version does not read them, and refuses to start while either file exists:

```json
{"error":{"code":"DAEMON_STARTUP_FAILED","message":"The daemon could not start: Found /Users/dana/.simlock/state.json, which this Simlock no longer reads. To upgrade: with the older Simlock, release every lease and run `simlock nuke --delete-devices`; then remove /Users/dana/.simlock/state.json and start again. ..."}}
```

Nothing carries over, so clear the old version's devices first.

<Aside type="caution">
These steps delete every device Simlock made on this machine and end every lease. Tell the agents using this machine first.
</Aside>

<Steps>

1. With the older Simlock installed, release every lease and delete its devices. Answer `y` when asked:

   ```sh
   simlock release --all
   simlock nuke --delete-devices
   simlock daemon stop
   ```

   If you already installed the new version, put the old one back for this step, for example with `npm i -g simlock@<old-version>`.

2. Remove the old files:

   ```sh
   rm ~/.simlock/state.json ~/.simlock/tokens.json
   ```

3. Install the new version and start it:

   ```sh
   npm i -g simlock
   simlock daemon start
   ```

4. If agents reached this worker over HTTP, their tokens are gone. Create new ones with `simlock token create --role agent`. See [Remote agents](/simlock/docs/using-devices/remote-agents).

</Steps>

On a gateway, remove the files the message names in `~/.simlock/gateway`, then create each worker's join token again and set it on that worker. See [Add a worker](/simlock/docs/gateway/joining-workers).

## When the daemon will not start

A command that cannot start the daemon fails with `DAEMON_STARTUP_FAILED`, and the message says why. A config mistake is caught before the start, and the error names the key. [Troubleshooting](/simlock/docs/worker/troubleshooting#the-daemon-will-not-start) lists each cause and its fix.
