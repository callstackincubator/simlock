**Result:** you know what the worker does now, what happened earlier, and how its devices were used.

| Command | Shows |
| --- | --- |
| `simlock status` | The machine now: capacity, devices, leases and the queue. |
| `simlock list --requests` | Why each waiting request waits. |
| `simlock events` | What happened, one JSON line per event. |
| `simlock stats` | How devices were used over a period. |
| `simlock daemon logs` | The daemon's own log. |

Each command except `daemon logs` starts the daemon if it is not running. The [web console](/simlock/docs/worker/console-and-http) shows the same in a browser.

## See the machine now

```sh
simlock status
```

```text
Running global: 3 + 1 reserved/6, warm 1
Capacity ios: managed 4/8, running 3 + 1 reserved/4, warm 1
Capacity android: managed 0/4, running 0 + 0 reserved/2, warm 0

```

| Line | What it tells you |
| --- | --- |
| `Daemon` | `starting`, `running` or `failed`, and whether it is a `worker` or a `gateway`. |
| `Simlock` | The daemon's version, with `(0.7.1 available)` when a newer release exists. The `CLI` line is the version of the `simlock` you ran. |
| `Updating to`, `Last update failed` | Shown only during or after an update. See [Update Simlock](/simlock/docs/worker/daemon#update-simlock). |
| `Console` | The web console's address. Shown only when HTTP is on. |
| `Host` | The operating system, CPU architecture, and the Xcode version the iOS tools report. |
| `Load` | CPU, memory, swap and free disk, and how many seconds ago they were read. A part that could not be read says `unavailable`. |
| `Memory pressure` | Shown only while the worker has paused warming or new devices because the host is short of memory: the step, when it began (local time) and why. See [Memory pressure](/simlock/docs/concepts/queue-and-capacity#memory-pressure). |
| `History` | Shown only when the event history has a problem. See [The event history is not written](/simlock/docs/troubleshooting/worker#the-event-history-is-not-written). |
| `Running global`, `Capacity`, `RAM budget` | How full the machine is. See [See how full the machine is](/simlock/docs/worker/capacity#see-how-full-the-machine-is). |
| `warm pool` | Targets and learned kinds, and why one is short. See [Read the warm pool](/simlock/docs/worker/warm-pool#read-the-warm-pool-in-simlock-status). |
| `Device` | One line per device: id, state, and its mode, or `physical` and its class for a phone. A baseline copy names its baseline. Markers in brackets flag a problem, such as `quarantined (purge retry 2, ...)` or `stalled`. |
| `Lease` | One line per lease: id, the requester, its label if it has one, and when it was granted and last renewed, in milliseconds since 1970. |
| `Install` | A runtime or system image being downloaded, for how long, and how many requests wait on it. |
| `Queue depth` | How many lease requests wait. |

A device's state is one of `provisioning`, `ready`, `leased`, `reclaiming`, `quarantined`, `absent` (a phone that is unplugged, locked or not trusted), `shutdown` or `deleted`. A deleted device stays listed for an hour (`devices.deletedRetentionMs`).

Right after the daemon starts, status prints `Devices, leases and capacity appear once startup finishes.` in place of the device lines. Run it again a few seconds later.

`simlock status --json` prints the same as one JSON object. To check whether the daemon runs without starting it, use `simlock daemon status`.

## See why requests wait

```sh
simlock list --requests
```

```text
Request req_3c8e1f52-9a4d-4b7e-8f20-6d1a5c9e3b74: codex:7a1d4e9b-2c3f-4e8a-b6d0-1f5c8a3e9d27, ios iPhone 16 18.4, queued at 1, waiting 42s — full: running limit for iOS
```

Each line shows who asked, the device it asked for, its place in the queue and why it waits. What each reason means and what to do: [A lease waits and never starts](/simlock/docs/troubleshooting/worker#a-lease-waits-and-never-starts).

## Follow the events

Simlock records an event for every lease, device, capacity, download and cleanup change:

```sh
simlock events --since 1h --follow
```

```json
{"id":"evt_2b7c9e14-5d3a-4f8e-a1c6-9e0d2b4f7a35","seq":812,"timestamp":1761037320412,"event":"lease.granted","payload":{"deviceId":"dev_6f1c2a9e-3b7d-4e0a-9c55-2d8f1e4a7b10","leaseId":"lse_9d2e7b14-6c3a-4f81-a0e5-7b1c9d4e2f36","requester":"claude-code:5f0e8a3c-1b2d-4c6e-9f7a-0d3b8e1c4a92","requestId":"req_1e4b8d2a-7c9f-4a3e-b5d1-2f6c9e0a8b43","source":"warm","platform":"ios"},"module":"lease-lifecycle"}
```

| Flag | What you get |
| --- | --- |
| none | The events the daemon holds in memory: the last 1,000 (`eventBuffer.capacity`) since it started. Empty after a restart. |
| `--since <duration>` | Events from the history on disk, which survives restarts and crashes. A duration is a number with `ms`, `s`, `m`, `h` or `d`, such as `30m` or `2d`; a bare number is milliseconds. Works with the daemon stopped, and does not start one. |
| `--follow` | New events until Ctrl-C. With `--since`, the history first, then live events, with nothing missed or printed twice. |

While following, each live event prints wrapped in an object with a `subscriptionId`, the event under `event`. Events replayed from history print bare. To watch every refused lease:

```sh
simlock events --follow | jq -c 'if .subscriptionId then .event else . end | select(.event == "lease.rejected")'
```

Every event and its fields: [Events](/simlock/docs/reference/events).

## Measure how devices were used

```sh
simlock stats --since 7d
```

```text
Usage from 2026-11-13T09:00:00.000Z to 2026-11-20T09:00:00.000Z

Totals
  Requests:     214 (209 granted, 5 rejected)
  Granted:      warm 160, booted 41, provisioned 8
  Rejected:     no-wait 3, timeout 2
  Wait:         p50 400ms, p95 38s, max 2m 10s (209 samples)
  Held:         p50 14m 2s, p95 52m 30s, max 3h 41m (205 samples)
```

The report goes on with turnaround, provisioning and boot times, slot, RAM and queue use, incidents, and a section per platform, per worker and per requester.

- With no flag the window is the last 24 hours. `--since 30d` counts back from now.
- `--from` and `--to` name both ends as ISO 8601 times with `Z` or an offset, such as `2026-11-15T00:00Z`. Without `--to`, the window ends now.
- A window is at most 90 days.
- If the worker has not kept figures for the whole window, a line says `Figures cover from ...` and the counts start there.
- `--json` prints one JSON object, with a series of up to 200 points for charts.
- `--csv` prints one row per lease request, for a spreadsheet, at most the newest 100,000. A notice on stderr says when the window had more.

## Choose how much history to keep

Times are in milliseconds. Restart the daemon after a change.

| Key | Default | What it keeps |
| --- | --- | --- |
| `eventLog.retention` | `604800000` (7 days) | How far back `simlock events --since` reaches. |
| `eventLog.maxBytes` | `268435456` (256 MiB) | The most disk the event history uses. When full, the oldest events go first. At least 16 MiB. |
| `metrics.retention` | `7776000000` (90 days) | How far back `simlock stats` counts. At least `eventLog.retention`. Figures stay after their events are pruned. |
| `eventBuffer.capacity` | `1000` | How many recent events plain `simlock events` shows. |

To keep 30 days of events:

```sh
simlock config set eventLog.retention 2592000000
simlock daemon stop
simlock daemon start
```

**Check:** `simlock config get eventLog.retention` prints `2592000000`.

## Read the daemon log

The daemon writes its own log, apart from the events, to `daemon.log` in the data folder. Read it when an error message is not enough.

```sh
simlock daemon logs            # the last 100 lines
simlock daemon logs --follow   # keep printing new lines
```

Each line is one JSON object with a time (milliseconds since 1970), a level, the part of the daemon that wrote it, and a message:

```json
{"timestamp":1761037402114,"level":"warn","module":"daemon","message":"Unknown config key: \"idle.shutdownAfter\""}
```

When the log reaches `log.rotateBytes` (5 MiB by default), it starts a new file. Simlock keeps one older file, `daemon.log.1`, and `simlock daemon logs` reads both.

`log.level` sets how much it writes: `debug`, `info` (the default), `warn` or `error`.

<Aside type="caution">
At `debug` the log records every command Simlock runs against the platform tools, and every read request. It grows fast. Set `log.level` back to `info` when you are done.
</Aside>

```sh
simlock config set log.level debug
simlock daemon stop
simlock daemon start
```

## When it fails

| What you see | Cause | Fix |
| --- | --- | --- |
| `HISTORY_UNAVAILABLE` from `simlock stats` | The history file cannot be read or written. | See [The event history is not written](/simlock/docs/troubleshooting/worker#the-event-history-is-not-written). |
| `HISTORY_NOT_KEPT`, exit 12 | The window ends before the oldest figures the worker keeps. | Ask for a later window. |
| `simlock events` prints nothing | The daemon restarted, and plain `events` shows only what it holds in memory. | Add `--since 1h`. |

Flags: [`simlock status`](/simlock/docs/reference/cli#simlock-status), [`simlock events`](/simlock/docs/reference/cli#simlock-events), [`simlock stats`](/simlock/docs/reference/cli#simlock-stats). Keys: [Configuration reference](/simlock/docs/reference/configuration#logging-and-history).
