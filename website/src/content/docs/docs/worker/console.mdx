The web console shows, in your browser, what your worker is doing: its devices, the leases on them, the requests waiting for a device, and anything that needs your attention. The daemon serves it, so there is nothing to install.

The console is for the people who run the worker. It only shows things: you cannot lease, release or fix anything from it. Agents keep using the CLI, the MCP server, the client and the HTTP API.

On a gateway the same console shows every worker in the fleet. See [Fleet console](/simlock/docs/gateway/fleet-console).

## Turn on the console

The console is on whenever HTTP is on, and HTTP is on by default on a standalone worker. There is no separate switch. A worker that has joined a gateway has no console of its own: use the gateway's console.

<Aside type="caution">
HTTP is a network listener, on by default on a standalone worker. By default it listens on `127.0.0.1:4701`, so only this machine can reach it. If you set `http.host` to `0.0.0.0` or another address, anyone who can reach that port can load the sign-in page and call the HTTP API with a token. Simlock does not do TLS: to reach the console from another machine, put a reverse proxy or a tunnel in front of it.
</Aside>

Start the daemon. `simlock daemon start` prints the console's address:

```sh
simlock daemon start
```

```text
Daemon running
Console: http://127.0.0.1:4701/
```

To turn HTTP off, run `simlock config set http.enabled false` and restart the daemon.

To listen on another address or port, set `http.host` and `http.port` with `simlock config set`, then restart. See [Configuration](/simlock/docs/worker/configuration).

## Open the console

Open the address `simlock daemon start` printed. `simlock status` prints the same `Console:` line after the daemon's health, and `simlock status --json` has it as `daemon.consoleUrl`. When HTTP is off there is no `Console:` line.

When `http.host` is `0.0.0.0` or `::`, the daemon listens on every interface and the address says `localhost`. From another machine, use this machine's name or address instead.

Every page has its own address, such as `/leases`, so you can bookmark a page, reload it, or share a link to it.

## Sign in with an operator token

The console asks for an operator token. Make one on the worker:

```sh
simlock token create --role operator --label alex-laptop
```

```json
{"secret":"slk_Qm9vdHN0cmFwIHRoZSBjb25zb2xlIGFuZCBzaWduIGl","token":{"id":"tok_3f9c2a1e-7b4d-4e8a-9c61-2d5f0b7a8e14","role":"operator","label":"alex-laptop","createdAt":1792569600000}}
```

Copy the `secret`, paste it into the **Operator token** field and press **Sign in**. The secret is printed only once, so keep it somewhere safe. A token works only on the daemon that made it.

If the console does not accept the token, it says why:

| Message | What it means |
| --- | --- |
| This daemon does not know that token. | The token is mistyped, revoked, or from another daemon. |
| That token is real, but the console needs an operator token. | It is an agent or worker token. Make one with `--role operator`. |
| The daemon is starting. Try again in a moment. | The daemon answers but has not finished starting. |
| The daemon cannot be reached. | Nothing answers at this address. Check `simlock daemon status`. |
| The daemon answered with an error (HTTP 500). | Anything else. The daemon's log says more: `simlock daemon logs`. |

The console keeps the token in this browser tab only. A reload keeps you signed in; a new tab asks again; closing the tab signs you out. **Sign out** at the bottom of the sidebar forgets the token at once. If you revoke the token with `simlock token revoke <token-id>`, the console signs you out the next time it asks the daemon for anything.

To sign people in through a sign-in proxy instead of tokens, see [Access control](/simlock/docs/gateway/access-control).

## Find your way around

The sidebar floats beside the page in its own card. Use the button beside the Simlock name to collapse or expand it. On a phone, open its menu above the page. It leads to every page: **Overview** and **Inbox**, then **Fleet**, **Leases**, **Queue** and **Baselines**, then **Activity** and **Usage**. **Inbox** shows how many items need you, on every page. At the bottom, the account box shows the connection, who you are signed in as, and a **Sign out** icon. Hover over the name to see it in full. On a gateway that is behind the latest release, a line above the account says, for example, `simlock 0.3.0 · 0.4.0 available`.

On **Queue**, **Inbox** and **Activity**, the item you select opens in a panel over the list. On **Leases**, it opens in a pane beside the table. On **Fleet**, a worker opens as its own page, and a device opens its streaming page. Lists show 25 rows at a time, with a pager for 50 or 100.

The console follows your system's light or dark setting and fits the window it is in. It is laid out for a 1440 pixel wide window, where each page fits without scrolling. In a narrower window the tiles take fewer columns and the Overview's right-hand cards move under its chart. Below 1280 pixels a lease opens as a panel over the list, and below 768 the sidebar becomes a bar at the top with a menu button and tables stack into blocks. No page scrolls sideways, down to a 360 pixel wide phone.

Pages update by themselves: a new lease or a booting device shows within about a second, and readings such as CPU load within 15 seconds. The bottom of the sidebar shows the connection:

| It says | What it means |
| --- | --- |
| Connected | Up to date. |
| Reconnecting — data from 12 s ago | The console lost the daemon. What you see is as old as it says. It keeps trying and catches up by itself. |
| Daemon is starting | The daemon is back and still starting up. |

## Overview

The console opens on **Overview**, the worker on one page. Under the title it says when it last updated. It has no tables.

- **Range**: **1 h**, **6 h**, **24 h** or **7 d**, at the top right. It sets the figures and charts below.
- **Banner**: when something needs you, a line counts the problems from **Inbox**, links the first one and says how many more there are. **Open Inbox** goes to the list. With nothing to do, there is no banner.
- **Tiles**: each one opens its page. **Leased** (leases held, of the devices running) and **Ready** (devices ready to lease) open **Leases** and **Fleet**; **Waiting** (with the longest wait) opens **Queue**; **Wait p95** for the range (how long the slowest 1 in 20 requests waited) opens **Usage** on the same range; **Ending soon** (leases with under 5 minutes left) opens **Leases**; **Workers** connected opens **Fleet**. A figure the daemon could not read shows a dash, never zero.
- **Fleet**: one tile per worker, with its status in a pill when something is wrong, its slots for iOS and Android, and its CPU, memory and disk. A worker with more than ten slots shows a meter and the leased/total fraction. **Open fleet** shows all of it.
- **Leases held**: a chart over the range, with the current and the highest figure. A table of the numbers is there for screen readers.
- **Capacity**: per platform, how much of the room your workers may run is leased.
- **Queue**: the three longest waiting requests, and **Ending soon**: the two leases that end first. Each row opens its request or lease. If the queue cannot be read, the card says so instead of showing it empty.
- **Requests waiting**: a bar for each period of the range. **Device slots in use** is on **Usage**.

## Fleet

**Fleet** shows the workers the daemon knows. On a worker that is one card: this machine. **Add worker** at the top links to [Join workers](/simlock/docs/gateway/joining-workers); it changes nothing in the console.

**All**, **Issues** and **Busy** narrow the list, and the search box beside them matches a worker's name, id or system. **Issues** shows workers with something wrong. **Busy** shows workers using three quarters of their device slots or more.

A worker with something wrong sits under **Needs attention** on a card. It has the name and system, a word and a colour for the worst thing wrong, and a line or two on why (for example how long a lost worker has been gone, or how full its disk is):

| Colour | When |
| --- | --- |
| Red | The worker's health is `failed`, its memory pressure is `critical`, or its CPU, memory or disk is 95% full or more. |
| Amber | The worker is `starting` or `over RAM budget`, its memory pressure is `warn`, or a figure is 85% full or more. |

Under that the card shows the iOS and Android slots, CPU, memory and disk with a bar each, how many leases the worker holds, and its actions: **Open** and **Details** go to the worker's page, **Undrain** appears on a drained worker, and a disconnected worker has **View leases**, a link to [Leases](#leases). Up to ten slots appear as squares; above ten, a meter shows the leased/total fraction. Slot state counts are available to screen readers. Unavailable load is shown as `—`, never as zero.

Every other worker sits under **Healthy**, as a compact tile with its leased slots over its total, its slots and its CPU, memory and disk. The tile's **⋯** menu offers the worker's actions. Under both groups, **Worker events** lists the workers' own events of the last hour, and new ones appear at the top.

Select a worker to open its page. Its title reads **Fleet / name**, with the worker's status beside it, and its system, version and the age of its last reading beneath. At the top right are the worker's first action, for example **Drain**, and **⋯** for the rest. Four rings show CPU, memory, disk and slots, each with its figure and a line of context. Unavailable load is not shown as zero. Below them, the card on the left shows:

- **Slots**: the iOS and Android slots, leased over total.
- **Host**: the operating system, the version of each platform tool, the simlock version, the devices kept warm, any optional module that is not available (such as screen streaming) with its reason, and the worker's id.
- **Baselines here**: the baselines saved on this worker, with their sizes.

The card on the right has two tabs:

- **Devices**: a tile for every device with its model, runtime and state. A leased device shows its holder, the time left on the lease and when it was granted; a device that is ready shows when it booted. **Watch** opens the device's screen.
- **Warm pool**: whether the worker keeps devices warm, the running slots it holds back, and per target and learned kind its origin (`configured` or `learned`), how many devices it wants, how many are ready and how many are booting. A target it cannot fill shows the reason, such as `runtime-missing`. Under it, **Installs in progress** lists runtimes and system images being downloaded. See [Capacity and the warm pool](/simlock/docs/worker/capacity).

Under the tabs, **Events on this worker** lists this worker's events, newest first. Older events load as you scroll down, and new ones appear at the top.

### Open a device

Select a device on the worker to open its drawer. It shows the model, runtime, state, the baseline and version the device was copied from (a device made from a baseline only), holder, lease and UDID, and a **Watch** link.

**Watch** opens the device's streaming page, at `/fleet/<worker>/devices/<device>/`, so a pasted link or a reload opens it too. The live screen plays in a phone-shaped frame, whether or not the device is leased. Two pills over it show the stream's own figures: `LIVE` with the frame rate, and the codec, picture size and bandwidth. At the right are the **Holder** card (the agent, the lease id, the time left and when it was renewed, with **Copy lease id**, **Lease details** and **Release**), the device's facts and its recent events. A device with no lease has no Holder card. The page only watches: it does not send taps or keys.

**Stop watching** closes the stream and returns to the worker's page; leaving the page any other way closes it too. A device that is not running says why instead of showing a picture, for example "The device is shut down. Its screen shows while it runs.", and the picture starts by itself once the device is `ready` again. If screen streaming is off for the worker, the page says "Streaming is off on" and the worker's name. See [Watch the screen](/simlock/docs/using-devices/watching-the-screen).

An older link that ends in `?drawer=screen` opens the streaming page. On a gateway it works the same, for a device on any connected worker.

### Update a worker

On a gateway, a worker that runs an older version than the gateway knows of shows `simlock 0.3.0 · 0.4.0 available` under its name on its card and on its page. The worker page's **⋯** menu, and the search (⌘K), offer **Update…**. The dialog says how many leases the worker holds: with none it installs at once; otherwise it takes no new leases and waits for them to end, then restarts by itself. Confirm with **Update** and a toast says `Updating <name> to <version>`; if the worker already updates you see `<name> is already updating to <version>`, and if it already runs the version, `<name> already runs <version>`.

While an update runs, the worker's state reads `updating` and its card says its stage: `waiting for 2 leases`, `installing` or `restarting`. A worker that waits for leases also offers **Update now**, which asks `Install <version> on <name> now?`; **Install now** restarts it at once, and its leases keep running through the restart. A disconnected worker offers no **Update now**. An incompatible worker, one that cannot talk to the gateway until it is updated, offers **Update…** whatever the latest version, and **Update now** once its update is waiting for leases.

If an update fails, the worker's page shows a red banner, `Update to 0.4.0 failed (installing): <message>`, with an **Update again** button, and the [Inbox](#inbox) lists it. The worker runs its old version again.

While the daemon is still starting, devices, capacity and the warm pool are left out. They appear once startup finishes.

## Leases

**Leases** lists every lease on the worker, the same leases `simlock list --leases` shows. Each row has the holder (**Held by**), the device and its runtime, the worker, and the time left (**Expires in**) as a countdown with a bar. A lease with less than 5 minutes left turns amber. **Ending < 5 min**, **iOS** and **Android** narrow the list, and the box beside them searches by holder, device and worker. Under the table, a line counts the rows shown; a list longer than one page gets a pager.

The holder is the identity that took the lease. A lease taken over the HTTP API shows the label of the token that took it, so give each agent's token a label:

```sh
simlock token create --role agent --label ci-runner-3
```

A lease taken with the CLI or MCP server on this machine shows the agent identity it was taken with.
Long holder names are shortened in the middle; hover over the holder link to see the complete requester identity. A chip identifies a known agent tool, or shows a dot when the tool is unknown.

Beside the table, a pane of fixed width summarises every lease, whatever the filter or search leaves in the table:

- **By holder**: how many leases each holder has.
- **By platform**: how many of the iOS and Android slots are leased.
- **Ending in 5 min**: the leases that end soonest, with their countdowns.
- **Longest held**: the leases held the longest.

Select a lease and the pane shows that lease instead, and the table does not move. It has the holder, a ring and countdown with the lease's original time, **Watch**, **Copy id** and **Release**, the device, worker, when it was granted, the token, the lease id, the device id and the baseline (only for a lease made from a baseline), and the **Recent events** about the lease from the last hour. **Watch** opens the device's streaming page and is offered only while the worker streams the device. **Copy id** copies the complete lease id; if the browser cannot copy, a message says so and the id stays on screen to select. **Release** asks for confirmation before it releases the lease. Close the pane to see the summary again.

In a window narrower than 1280 pixels the lease opens as a panel over the page instead, and the summary sits under the table.

A lease that was released or has expired says "This lease is not held."

## Queue

**Queue** lists every request waiting for a device, the same requests `simlock list --requests` shows. Above the list, **Wait p95** shows how long requests waited in the last hour.

Each row has the request's place in its queue, the agent that asked, how long it has waited, the device it asked for, and its stage: `queued` while it waits its turn, `starting` while the daemon finds, creates, boots or downloads a device for it.

Select a request to see when it was made, its place, its stage and, for a `queued` request, why the daemon could not place it yet:

| Why | What it means |
| --- | --- |
| Behind an earlier request | Another request for the same kind of device came first. |
| Full: device limit | The worker already has as many devices as it may keep. |
| Full: running limit | The worker runs as many devices as it may. |
| Full: running limit for iOS | The worker runs as many iOS devices as it may (or Android). |
| Full: RAM budget | Booting another device would go over the worker's RAM budget. |
| A matching device is starting | A device that fits is booting and will serve it. |
| Every matching device is leased or absent | The request names physical devices that are all in use or unplugged. |

A request leaves the list as soon as it gets its device, fails or is cancelled. To change how many devices the worker runs, see [Capacity and the warm pool](/simlock/docs/worker/capacity).

## Baselines

**Baselines** lists every baseline the worker holds, grouped by platform. A group's heading gives its baseline count and their size together; when some sizes are not known, the size says `known`. Each row shows the baseline's name, the model and runtime it was saved on, its size, when it was built, and a `ready` or `stale` state. A stale baseline shows its reason under the state, word for word. Use **All**, **Stale** and **Ready** to narrow the list, and the search box to find a baseline by name, model, runtime or worker. The group counts follow the filter and the search.

Under the table, **Disk used by baselines** shows, for each worker, how much of its own disk its baselines take. A bar is that worker's baseline size against that worker's disk, and its figure is printed beside it. A size or a disk total the worker has not reported is shown as unknown, never as zero.

**Prepare baseline**, above the page, opens the guide to preparing one. The console does not save baselines itself.

To save or remove a baseline, use `simlock baseline save` and `simlock baseline remove` on the command line; see [Baselines](/simlock/docs/worker/baselines).

## Inbox

**Inbox** lists everything on the worker that needs you. Each row is the condition and the worker or device it is about. An item leaves the list as soon as the daemon reports that it cleared, and its page then says "Resolved." The console shows these items; it does not fix them.

| Item | What it means | What to do |
| --- | --- | --- |
| `over RAM budget` | The devices on the worker use more RAM than its budget allows. `simlock status` shows the same as `(over limit)`. | Release leases, or lower the device limits. See [Capacity and the warm pool](/simlock/docs/worker/capacity). |
| `quarantined` | Simlock could not clean up a device. Its **Cause** says what failed: `Purge failed`, `Shutdown failed`, `Delete failed`, or `Stalled while provisioning` or `reclaiming`. Simlock retries the cleanup in the background and leases the device to no one meanwhile. | Wait for the retry, or see [Troubleshooting](/simlock/docs/worker/troubleshooting). |
| `stalled` | A device has been `provisioning` or `reclaiming` for longer than it should take, with nothing working on it. `simlock doctor` reports the same devices. | See [Troubleshooting](/simlock/docs/worker/troubleshooting). |

On a gateway the list also has `update failed`: the update of a worker failed, with **Update…** as its fix. The facts are **From**, **To**, **Stage** and **When**. The list also has `disconnected`, `incompatible` and `drained` workers; a single worker never shows those. See [Fleet console](/simlock/docs/gateway/fleet-console).

Select an item to see the facts that matter for it, such as how much RAM the worker uses of its budget, and the events of the last hour about that device or worker.

## Activity

**Activity** lists events newest first, starting with the last hour. New events appear at the top as they happen, and older ones load as you scroll down. Each row shows the event's name, what it is about, the worker and the time. The search box and the range (**1 h**, **6 h**, **24 h** or **7 d**) are in the page header. If the events loaded do not reach back as far as the range, the page says so, and **Load older events** fetches more.

A card on the left filters the list by **Kind** (**Leases**, **Queue**, **Devices**, **Workers**, **Baselines** or **Other**), by state (**Problems only**) and by **Worker**. Each option shows how many events it would show. Tick several options in a group to see all of them; tick none to see everything. Events with no worker are under **Other** in the Worker group. Above the list, a chart counts the events shown per minute over the last hour.

Select an event to see its whole payload and a link to the lease, worker, request or Inbox item it is about. For what each event means, see [Events](/simlock/docs/reference/events).

## Usage

**Usage** shows the figures for a range, the same numbers `simlock stats` gives: requests, grants, rejections, the wait and hold times, grants by source (warm, booted or provisioned), rejections by reason, device incidents, and the figures per platform and per requester. Pick **1 hour**, **6 hours**, **24 hours** or **7 days**. See [Monitoring](/simlock/docs/worker/monitoring).
