## Global flags

These flags work anywhere on the command line, before or after the command.

| Flag | Meaning | Default |
| --- | --- | --- |
| `--token <secret>` | Connect as admin with this token. `--token=<secret>` also works. | See [Admin credential](#admin-credential) |
| `--gateway` | Send the command to this machine's gateway, the daemon in `~/.simlock/gateway`. Takes no value. | See [Which daemon a command reaches](#which-daemon-a-command-reaches) |
| `--local` | Send the command to this machine's worker, the daemon in `~/.simlock`. Takes no value. | See [Which daemon a command reaches](#which-daemon-a-command-reaches) |
| `--help`, `-h` | As the first word, or with no command: print the list of commands. | — |

`--gateway` and `--local` together are a usage error, and so is `--gateway=yes` or `--local=yes`.

<Aside type="caution">
The CLI takes these flags out of the whole command line, including the arguments after `simctl` and `adb`. `simlock adb shell echo --local` runs `adb shell echo` against the worker. Quote or rename an argument that collides with one of them.
</Aside>

### Which daemon a command reaches

With `--gateway`, the command goes to the gateway. With `--local`, it goes to the worker. With neither, it goes to the gateway only when this machine has a gateway (`~/.simlock/gateway` holds an `instance.json` or `config.json`) and no worker has started here yet (`~/.simlock/instance.json` does not exist). Otherwise it goes to the worker.

`simlock --gateway <command>` on a machine with no gateway fails with `GATEWAY_NOT_PRESENT` (exit 2) and starts nothing. These commands are exempt, because they create the gateway, run before it or never contact a daemon: `daemon start`, `daemon install`, `daemon uninstall`, `config set`, `mcp`, `instructions` and `setup`.

When a worker refuses a gateway-only command, such as `worker drain`, and a gateway also runs on this machine, the error message ends with `A gateway also runs on this machine: run the command again with --gateway.`

### Admin credential

Most commands that change or inspect the whole machine need the admin role. The CLI uses the first credential it finds:

1. `--token <secret>`.
2. The `SIMLOCK_ADMIN_TOKEN` environment variable.
3. The `admin.token` file the daemon writes into its data folder (`~/.simlock` for a worker, `~/.simlock/gateway` for a gateway).

If none is found, or the daemon rejects the one found, the CLI connects as an agent and writes one notice line to stderr:

```json
{"notice":"admin credential unavailable; connecting as agent (admin-only commands will fail with FORBIDDEN)"}
```

An admin-only command then fails with `FORBIDDEN` (exit 1). On the machine where the daemon runs, as the same user, the `admin.token` file makes you admin with no setup.

### The daemon starts on demand

A command that needs the daemon starts it when nothing is listening. The CLI checks the configuration first, so a bad `config.json` fails on the command's stderr. If the daemon does not answer within 20 seconds, or exits while starting, the command fails with `DAEMON_STARTUP_FAILED` (exit 1) and the message carries the daemon's own start error. `daemon stop`, `daemon status` and `events --since` (without `--follow`) never start a daemon.

## simlock lease

Lease a device. The command waits for a device, prints the grant, then stays running: it renews the lease and releases it when the command ends. See [Lease lifecycle](/simlock/docs/using-devices/lease-lifecycle) and [Choosing a device](/simlock/docs/using-devices/choosing-a-device).

```text
simlock lease --platform <ios|android> [--device <model> | --class <class>]
              [--os <version|range>] [--mode <slim|full>] [--image-tag <tag>] [--agent-id <id>]
              [--timeout <duration>] [--lease-id <id>] [--physical]
              [--no-wait] [--detach] [--ttl <duration>] [--allow-download]
              [--export-env] [--bind-pid <pid>]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--platform <ios or android>` | The platform to lease on. Required. | — |
| `--device <model>` | An exact model, such as `"iPhone 16"` or `"Pixel 9"`. Cannot be combined with `--class`. | None |
| `--class <class>` | Any model of this class: `phone`, `tablet`, `watch`, `tv`, `vision`, `auto` or `desktop`. | `phone` when `--device` is not given |
| `--os <version or range>` | An exact OS version (`18.4`, `35`), or a range such as `>=18 <26` or `18 - 26`. A range never downloads. | The newest runtime installed for the platform |
| `--mode <slim or full>` | The device mode. `full` is guaranteed; `slim` is best effort and falls back to `full`. | The serving worker's default mode (`full` unless configured) |
| `--image-tag <tag>` | Android only: the system image type, such as `google_apis_playstore`. Never downloads. | Simlock picks an installed image |
| `--agent-id <id>` | The requester identity for this lease. Must not be empty. | See [Requester identity](#requester-identity) |
| `--timeout <duration>` | How long to wait in the queue before failing with `QUEUE_TIMEOUT` (exit 10). | No limit: waits until a device is free |
| `--lease-id <id>` | The ID the lease gets, in place of a generated one. 1 to 64 letters, digits, `-` and `_`, starting with a letter or digit. | A generated ID |
| `--physical` | Lease an enrolled physical device. Cannot be combined with `--mode`, `--image-tag` or `--allow-download`. | Off: simulators and emulators only |
| `--no-wait` | Fail with `NO_CAPACITY` (exit 11) instead of waiting in the queue. | Off |
| `--detach` | Print the grant and exit. Nothing renews or releases the lease after that. | Off |
| `--ttl <duration>` | How long the lease lives without a renew. More than `lease.maxTtlMs` (4h by default) is a `BAD_REQUEST`. | `lease.defaultTtlMs` (15m by default) |
| `--allow-download` | Allow Simlock to download a missing runtime or system image. `downloads.policy` can force downloads on (`always`) or off (`never`). Has no effect through a gateway. | Off |
| `--export-env` | Print the lease's environment as shell `export` lines in place of the JSON grant, for `eval "$(...)"`. | Off |
| `--bind-pid <pid>` | Release the lease when this process exits, in place of the command's parent. Positive integer. Ignored with `--detach`. | The parent process |

Without `--detach`, the command renews the lease every third of its TTL and releases it on `SIGINT`, `SIGTERM`, or when the watched process exits. It exits:

- 0 after it released the lease on request.
- 14 when the daemon ended the lease first (TTL expiry, an operator's `release`, or a device that could not be recovered). A `lease-lost` line on stderr says why.
- 1 with `DAEMON_CONNECTION_LOST` when the connection to the daemon dropped. The lease is not released and stays yours until its deadline; the stderr line names it.

### simlock lease renew

Push a lease's deadline out. Use it for a lease taken with `--detach`. Renewing a lease taken under a different [requester identity](#requester-identity) needs the admin role.

```text
simlock lease renew <lease-id> [--ttl <duration>]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `<lease-id>` | The lease to renew. Required. | — |
| `--ttl <duration>` | The new TTL, up to `lease.maxTtlMs`. | The TTL the lease was granted with |

Prints the renewed lease as one JSON line.

## simlock release

Give a lease back. The command returns as soon as the lease ends; the device is cleaned in the background. See [Lease lifecycle](/simlock/docs/using-devices/lease-lifecycle).

```text
simlock release <lease-id>
simlock release --all [--yes]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `<lease-id>` | The lease to release. | — |
| `--all` | Release every lease on the daemon. Needs the admin role. Asks for confirmation. | Off |
| `--yes` | Skip the confirmation for `--all`. Required when there is no terminal to ask in. | Off |

Releasing a lease taken under a different [requester identity](#requester-identity) needs the admin role. A lease ID and `--all` together are a usage error.

## simlock simctl

Run `xcrun simctl` against Simlock's iOS device set. Simlock's simulators live in their own set, so a bare `xcrun simctl` does not see them. See [Working with a device](/simlock/docs/using-devices/working-with-a-device).

```text
simlock simctl [--lease <lease-id>] <simctl-args...>
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--lease <lease-id>` | Through a gateway: the lease whose device the command runs against. Must come before the simctl arguments. On a worker it is accepted and ignored. | Through a gateway: your only lease |
| `<simctl-args...>` | Passed to `xcrun simctl` as written. | — |

Every other argument goes to `simctl`, including `--help`. On a worker the command runs on this machine with your terminal. Through a gateway it runs on the worker that holds the lease, its output is streamed back, and a piped stdin is sent along. The command exits with `simctl`'s own exit code; a Simlock failure also writes a `{"error":...}` line to stderr. Through a gateway the worker puts the lease's UDID into a command that leaves the device out, so write `simlock --gateway simctl install ./MyApp.app`. Simlock refuses `create`, `erase`, `delete`, `shutdown all`, `runtime delete`, a caller-supplied `--set` or `--profiles`, and (through a gateway) a command that names another device such as `booted`, with `PASSTHROUGH_REFUSED` (exit 2). Use `simlock release` and `simlock cleanup` to give devices back.

## simlock adb

Run `adb` against Simlock's adb server, which is where Simlock's emulators are. See [Working with a device](/simlock/docs/using-devices/working-with-a-device).

```text
simlock adb [--lease <lease-id>] <adb-args...>
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--lease <lease-id>` | Through a gateway: the lease whose device the command runs against. Must come before the adb arguments. On a worker it is accepted and ignored. | Through a gateway: your only lease |
| `<adb-args...>` | Passed to `adb` as written. | — |

The command exits with `adb`'s own exit code. Simlock refuses `adb kill-server`, flags that move adb to a different server, and (through a gateway) `adb shell` with no command, with `PASSTHROUGH_REFUSED` (exit 2). `-s`, `-t`, `-d` and `-e` are allowed before the subcommand. Through a gateway the worker adds `-s <serial>` for an emulator, and refuses `-s` with another serial, `-e`, `-d` and `-t`.

```text
simlock catalog [--platform <ios|android>] [--json]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--platform <ios or android>` | Show one platform only. | Both |
| `--json` | Print one JSON line in place of the text view. | Off |

## simlock mcp

Start Simlock's MCP server on stdin and stdout, for an agent to call. It offers the tools `list_devices`, `lease_simulator`, `release_simulator`, `lease_status` and `run_on_device`. See [Connect your agent](/simlock/docs/getting-started/connect-your-agent).

```text
simlock mcp
```

Takes no flags other than the [global flags](#global-flags). Stdout carries only MCP messages; diagnostics go to stderr. The server starts the daemon on the first tool call that needs it, and releases its lease when it exits.

## simlock instructions

Print the rules for using Simlock as one Markdown text: what every agent must do, then agent-device, iOS builds, the `simlock` CLI and MCP. Paste it into your agent's instructions. See [Connect your agent](/simlock/docs/getting-started/connect-your-agent).

```text
simlock instructions [--json]
```

| Flag | Meaning |
| --- | --- |
| `--json` | Print one JSON object, `{"instructions": "..."}`, instead of the text. |

The text is the same on every machine, and the command never contacts a daemon, so it works with no daemon running.

## simlock setup

Install a small `simlock` skill into Claude Code and Codex, so every later agent session there knows what Simlock is, checks its setup with `simlock whoami` and reads the rules with `simlock instructions`. The skill holds no rules itself, so it stays right after you update Simlock. See [Connect your agent](/simlock/docs/getting-started/connect-your-agent).

```text
simlock setup [--user | --project] [--tool <claude-code|codex>] [--mcp | --no-mcp] [--json]
```

| Flag | Meaning |
| --- | --- |
| `--user` | Install for your user, for every project. The default. |
| `--project` | Install for the project in the current directory only. |
| `--tool <claude-code\|codex>` | Install for this tool, even when it is not set up on this machine. Without it, `setup` installs for each tool whose directory (`~/.claude`, `~/.codex` or `$CODEX_HOME`) exists, and reports the other as `skipped`. |
| `--mcp` | Also connect Simlock's MCP server, by running the tool's own `mcp add` command. |
| `--no-mcp` | Do not connect it, and do not ask. |
| `--json` | Print the report as one JSON object, `{"scope": ..., "tools": [...]}`, and ask nothing. |

In a terminal, `setup` asks for the scope (`Install only for this project (not every project)? [y/N]`) and, for each tool it installs, whether to connect the MCP server too. The defaults are the user scope and no MCP. With no terminal, or with `--json`, it asks nothing and takes the defaults unless a flag says otherwise.

The skill is one file, `SKILL.md`, in a `simlock` directory under the tool's skills directory:

| Tool | User scope | Project scope |
| --- | --- | --- |
| Claude Code | `~/.claude/skills/simlock/` | `.claude/skills/simlock/` |
| Codex | `~/.agents/skills/simlock/` | `.agents/skills/simlock/` |

`setup` touches nothing outside the `simlock` directory. Run again, it replaces the directory's contents. If a file or a symlink sits where the `simlock` directory goes, it fails with `SETUP_REFUSED` (exit 2) before writing anything for any tool.

The MCP server is connected with `claude mcp add -s user simlock -- simlock mcp` (`-s project` at the project scope) and `codex mcp add simlock -- simlock mcp`. Codex has no project scope for MCP, so at the project scope `--mcp` reports `skipped` for it. A tool that is not on `PATH` is reported `skipped`; a command that fails or runs longer than 30 seconds is reported `failed`, and the command then exits 1 with `SETUP_MCP_FAILED` after the report.

The report has one `skill` line per tool and, when MCP was asked for, one `mcp` line:

```text
claude-code  skill  wrote      /Users/me/.claude/skills/simlock
claude-code  mcp    connected
codex        skill  skipped    /Users/me/.agents/skills/simlock  (Codex not found here; pass --tool codex to install anyway)
```

Skill statuses are `wrote`, `replaced` and `skipped`; MCP statuses are `connected`, `already`, `failed` and `skipped`. The command never contacts a daemon.

## simlock status

Show the daemon's health and mode, the Simlock version it runs, its console address, capacity, devices, leases and queue depth. Works for any caller. See [Monitoring](/simlock/docs/worker/monitoring).

When the daemon has seen a newer Simlock version on npm, the `Simlock:` line says so: `Simlock: 0.3.0 (0.4.0 available)`. A daemon learns the newest version at start and every 24 hours after, unless `update.check` is `false`.

While an update runs, the second line below `Daemon:` reads `Updating to <version>: waiting for 2 leases` (then `installing`, `restarting`). After an update that failed, `Last update failed (<stage>): <message>` stays until the next update starts or the daemon restarts without one.

```text
simlock status [--json]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--json` | Print one JSON line in place of the text view. | Off |

## simlock list

List one kind of record as JSON. Needs the admin role. See [Monitoring](/simlock/docs/worker/monitoring).

```text
simlock list [--devices|--leases|--rules|--requests]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--devices` | Every device the daemon manages. | Used when no flag is given |
| `--leases` | Every active lease. | Off |
| `--rules` | The cleanup rules. | Off |
| `--requests` | The requests waiting for a device, as text: who asked, for what, how long, and why each waits. | Off |

Only one of the four flags at a time.

## simlock events

Print business events, one JSON line each. Needs the admin role. See the [events reference](/simlock/docs/reference/events).

```text
simlock events [--follow] [--since <duration>]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--since <duration>` | Read events from this far back, from the history on disk, which survives restarts. | Off: only the recent events the daemon holds in memory (up to `eventBuffer.capacity`, 1000 by default), which start empty after a restart |
| `--follow` | Keep printing live events until you press Ctrl-C. With `--since`, prints the history first, with no gap and no duplicates. | Off |

`--since` without `--follow` reads the history file directly when no daemon is running, and does not start one.

## simlock stats

Show usage figures for a time window: requests, wait and hold times, provisioning and boot times, capacity and incidents, split by platform, worker and requester. Needs the admin role. See [Monitoring](/simlock/docs/worker/monitoring).

```text
simlock stats [--since <duration> | --from <ISO> [--to <ISO>]] [--json | --csv]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--since <duration>` | The window ends now and starts this long ago. Cannot be combined with `--from`. | `24h` |
| `--from <ISO time>` | The window's start, in ISO 8601 with `Z` or an offset, such as `2026-10-01T00:00:00Z`. | — |
| `--to <ISO time>` | The window's end. Needs `--from`. | Now |
| `--json` | Print one JSON line in place of the text view. | Off |
| `--csv` | Print every request in the window as CSV, one row each. Cannot be combined with `--json`. | Off |

The CSV holds at most the newest requests of the window up to a fixed limit; when it is cut short, a `notice` line on stderr says so. A window that ends before the oldest figure the history holds fails with `HISTORY_NOT_KEPT` (exit 12).

## simlock daemon

Start, stop and inspect the daemon. See [Running the daemon](/simlock/docs/worker/running-the-daemon).

```text
simlock daemon start [--json]
simlock daemon stop [--json]
simlock daemon status [--json]
simlock daemon logs [--follow | --json]
simlock daemon install [--json]
simlock daemon uninstall [--json]
```

| Subcommand | What it does |
| --- | --- |
| `start` | Start the daemon if it is not running and print `Daemon running` with the console address. `simlock --gateway daemon start` creates the gateway on first run. |
| `stop` | Ask the daemon to stop and print `Daemon stopping`. Needs the admin role. Never starts a daemon. |
| `status` | Print the daemon's status, or `Daemon stopped` when none is running, then on macOS and Linux one `Service:` line: `not installed`, `installed (launchd, <name>)`, `not loaded (launchd, <name>): commands start the daemon without it` or `broken (launchd, <name>): <path> is gone; run simlock daemon install` (`<path>, <path> are gone` for two). Never starts a daemon. Exits 1 when a daemon answers but refuses the connection, with no `Service:` line. |
| `logs` | Print the last 100 lines of `daemon.log`. |
| `install` | macOS and Linux only. Stop a running daemon (leases are kept), add a LaunchAgent (macOS) or a systemd user unit at `$XDG_CONFIG_HOME/systemd/user/<name>.service`, else `~/.config/systemd/user/<name>.service` (Linux) for this role and start the daemon through it. Prints `Service installed: <name> (launchd)` or `(systemd)`, `Daemon running` and a hint: `To start after a reboot, turn on automatic login for this user.` on macOS, `To start after a reboot without logging in, run: loginctl enable-linger <user>` on Linux. Without linger the last logout stops the user's systemd, the daemon and its emulators with it. On another platform it is a usage error: `daemon install is supported on macOS and Linux only`. |
| `uninstall` | Stop a running daemon, unload the LaunchAgent or systemd unit and delete its file. Prints `Service removed: <name> (launchd)`, or `Service not installed: <name>` when there is none (exit 0). |

| Flag | Meaning | Default |
| --- | --- | --- |
| `--json` | Print one JSON line in place of the text. `start` prints `{"status":"running"}`, `stop` prints `{"status":"stopping"}`, `status` prints the status or `{"status":"stopped"}`, each plus the `service` object on macOS, `logs` prints `{"logs":"..."}`, `install` prints `{"status":"installed","stopped":true,"service":{...}}` (`stopped` only when a daemon was running), `uninstall` prints `{"status":"removed"}` or `{"status":"not-installed"}` plus the same `service` object. | Off |
| `--follow` | `logs` only: keep printing new lines, across log rotations, until Ctrl-C. Cannot be combined with `--json`. | Off |

## simlock config

Read or change the daemon's configuration. See [Configuration](/simlock/docs/worker/configuration) and the [configuration reference](/simlock/docs/reference/configuration) for every key.

```text
simlock config
simlock config get <key>
simlock config set <key> <value>
```

| Subcommand | What it does |
| --- | --- |
| (none) | Print the daemon's whole effective configuration as one JSON line. Needs the admin role. |
| `get <key>` | Print one value. `<key>` is a dotted path, such as `lease.defaultTtlMs`. An unknown key is a usage error. Needs the admin role. |
| `set <key> <value>` | Write one value to `config.json` in the daemon's data folder. `<value>` is read as JSON when it parses (`900000`, `true`, `["ios"]`), else as a string. Does not contact the daemon. |

`config set` checks the whole file after the change and refuses an invalid value or an unknown key with a usage error (exit 2), leaving the file as it was. The file is written with owner-only permissions. A change takes effect the next time the daemon starts; the command prints `Updated <key> in <path>; takes effect on daemon restart.`

None of the subcommands take flags.

## simlock doctor

Check this machine's prerequisites and compare the daemon's records with the devices that exist. Findings you must act on go to stderr as text; the full report goes to stdout as one JSON line. See [Troubleshooting](/simlock/docs/worker/troubleshooting).

```text
simlock doctor [--fix] [--purge-orphans] [--yes]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--fix` | Apply the safe corrections to the records. Needs the admin role. Never installs a prerequisite. | Off: report only |
| `--purge-orphans` | Destroy every orphaned device: a device in Simlock's device folders with no record. Needs the admin role. Asks for confirmation. | Off |
| `--yes` | Skip the confirmation for `--purge-orphans`. Required when there is no terminal to ask in. | Off |

On a worker whose login service names a Node or `main.js` that is gone, the report holds a `service-broken` finding and stderr gets `Service broken: <name> (<manager>) names missing <path>. Run `simlock daemon install` again.` (`<path>, <path>` for two).

A gateway refuses `doctor` with `UNSUPPORTED_IN_GATEWAY_MODE` (exit 2): run it on each worker.

## simlock update

Install the newest Simlock, or a named version, on this machine and restart its daemon once the leases it holds have ended. Needs the admin role. See [Running the daemon](/simlock/docs/worker/running-the-daemon#update-simlock).

```text
simlock update [--version <version>] [--force] [--json]
```

| Flag | Meaning | Default |
| --- | --- | --- |
| `--version <version>` | Install this exact version (`0.4.0`, `0.4.0-rc.1`), older ones included. A tag or a range is a usage error. | The newest release |
| `--force` | Do not wait for the leases to end. They survive the restart. | Off |
| `--json` | Print no progress, only the daemon's final answer as one JSON line. | Off |

While the daemon waits, it takes no new leases: a request gets `DAEMON_UPDATING`. Leases already held renew and release as usual. The command follows the update and prints each stage. `Ctrl-C` stops following and leaves the update running; `simlock update --force` from another shell stops the wait.

```text
$ simlock update
Updating simlock 0.3.0 → 0.4.0
Waiting for 2 leases to end. Ctrl-C stops following; simlock update --force stops waiting.
Installing simlock@0.4.0
Restarting the daemon
simlock 0.4.0 is running
```

- Already on the newest release: `simlock 0.4.0 is already the latest`, and nothing restarts. A prerelease newer than the newest release is not downgraded; name the version to install another.
- The install fails: `Update failed (installing): <npm's message>`, exit 1. The old daemon keeps running and takes leases again.
- The new version does not start: the old version is installed again and started. `Update failed (restarting): <reason>. Rolled back to <version>.`, exit 1.
- The daemon does not answer within 15 minutes after it restarts: `The daemon did not come back; run simlock status.`, exit 1.
- Simlock must be installed with `npm i -g simlock`. Otherwise the command stops with `UPDATE_UNSUPPORTED_INSTALL`. A worker and a gateway of one user share the install, so while the other runs it stops with `UPDATE_SHARED_INSTALL`. npm failing to find the version is `UPDATE_RESOLVE_FAILED`. See [Errors](/simlock/docs/reference/errors#updating-simlock).

`POST /v1/update` does the same over HTTP. On a machine that runs a gateway, `simlock update --gateway` updates the gateway itself. A gateway holds no leases of its own, so it does not wait: it installs and restarts at once, and a request in that gap fails as in any gateway restart. To update a worker from a gateway, use [`simlock worker update`](#simlock-worker).

</Aside>


| `--delete-devices` | Also delete every device Simlock manages. | Off |
| `--yes` | Skip the confirmation. Required when there is no terminal to ask in. | Off |

A gateway refuses `nuke` with `UNSUPPORTED_IN_GATEWAY_MODE` (exit 2).

## simlock component

Install, list and remove iOS simulator runtimes and Android system images. See [Runtimes and images](/simlock/docs/worker/runtimes-and-images).

```text
simlock component install <ios|android> <version> [--worker <id>... | --all-workers]
simlock component list [--platform <ios|android>]
simlock component remove <ios|android> <version> [--dry-run] [--yes]
```

### simlock component install

Install one runtime or system image. Needs the admin role. Progress goes to stderr as JSON lines; the result goes to stdout as one JSON line.

| Flag | Meaning | Default |
| --- | --- | --- |
| `<ios or android> <version>` | The platform and the version to install, such as `ios 18.4` or `android 35`. Required. | — |
| `--worker <id>` | On a gateway: install on this worker. Repeat for more workers. | — |
| `--all-workers` | On a gateway: install on every worker. Cannot be combined with `--worker`. | — |

Without a worker flag the component installs on the machine the daemon runs on, and a gateway refuses with `UNSUPPORTED_IN_GATEWAY_MODE`. With a worker flag, a worker refuses with `UNSUPPORTED_IN_WORKER_MODE`. On a gateway, the command exits 15 when any worker did not end `installed` or `already-installed`; the per-worker result on stdout says which.

### simlock component list

| Flag | Meaning | Default |
| --- | --- | --- |
| `--platform <ios or android>` | List one platform only. | Both |

### simlock component remove

Remove a runtime or system image that Simlock installed. Needs the admin role.

| Flag | Meaning | Default |
| --- | --- | --- |
| `<ios or android> <version>` | The component to remove. Required. | — |
| `--dry-run` | Report what would be removed, without removing it or asking. | Off |
| `--yes` | Skip the confirmation. Required when there is no terminal to ask in. | Off |

Simlock refuses to remove a component it did not install (`COMPONENT_NOT_OWNED`) or one a device still uses (`COMPONENT_IN_USE`). A gateway refuses `component list` and `component remove` with `UNSUPPORTED_IN_GATEWAY_MODE`.

## simlock worker

List the workers of a gateway and take them in and out of service. See [Managing workers](/simlock/docs/gateway/managing-workers).

```text
simlock worker list [--json]
simlock worker drain <worker-id>
simlock worker undrain <worker-id>
simlock worker remove <worker-id>
simlock worker update <worker-id> [--version <version>] [--force] [--detach]
```

| Subcommand | What it does |
| --- | --- |
| `list` | Show each worker: connection, devices, capacity and installs. A worker's line also shows its Simlock version, with `(<latest> available)` when npm has a newer release, and `updating to <version>: <stage>` while it updates. On a single machine it shows the machine itself. `--json` prints one JSON line in place of the text view. |
| `drain` | Stop sending new requests to the worker. Its leases run on. |
| `undrain` | Send new requests to the worker again. |
| `remove` | Forget a worker that is not connected. A connected worker is refused with `WORKER_CONNECTED`: drain it and let it disconnect first. |
| `update` | Update one worker's Simlock from the gateway and follow it. The worker takes no new leases while it updates. A drain stays as it is. |

All five need the admin role. `drain`, `undrain` and `remove` print one JSON line, and on a worker all but `list` fail with `UNSUPPORTED_IN_WORKER_MODE` (exit 2).

`update` takes the flags of [`simlock update`](#simlock-update) and one more:

| Flag | Meaning | Default |
| --- | --- | --- |
| `--version <version>` | Install this exact version on the worker. | The newest release |
| `--force` | The worker does not wait for its leases to end. | Off |
| `--detach` | Print where the update started and return. Follow it with `simlock worker list`. | Off |

It follows the worker's line in the list and ends with one of these:

- `mac-studio-2 (3f81a2c4) is running 0.4.0`
- `Update failed (installing): <message>`, exit 1. The worker keeps running its old version and takes leases again.
- `mac-studio-2 (3f81a2c4) is already on the latest (0.4.0)`.
- With `--detach`: `Updating mac-studio-2 (3f81a2c4) 0.3.0 → 0.4.0. Follow it with simlock worker list.`

A worker that shows `incompatible` can be updated this way too. A worker that is not connected fails with `WORKER_NOT_CONNECTED`; one that does not answer within 90 seconds fails with the same code. `POST /v1/workers/{id}/update` does the same over HTTP.

## Output

Simlock is built for agents, so most output is JSON lines.

| Stream | What goes there |
| --- | --- |
| stdout | The command's result. JSON by default, one line, for `lease`, `lease renew`, `release`, `list`, `events`, `cleanup`, `doctor`, `nuke`, `config`, `config get`, `token`, `component`, and `worker drain`, `undrain` and `remove`. A text view by default, with `--json` for one JSON line, for `status`, `catalog`, `stats`, `whoami`, `daemon`, `worker list`, `alerts test` and `device`. `list --requests`, `config set` and `lease --export-env` print text only. |
| stderr | Progress and notices as JSON lines, and the error line when a command fails. `doctor` also writes the findings you must act on here as text. |

A lease in progress writes lines like these to stderr:

```json
{"push":"progress","stage":"queued","queuePosition":1}
{"push":"progress","stage":"booting","etaMs":60000}
{"push":"device-unhealthy","leaseId":"3f6c2a9e-8b1d-4c57-9e0a-5d2b7f41c8e3","deviceId":"7d1e0b52-4a3c-4f8e-b6a9-2c5d8e9f1a04"}
{"push":"lease-lost","leaseId":"3f6c2a9e-8b1d-4c57-9e0a-5d2b7f41c8e3","deviceId":"7d1e0b52-4a3c-4f8e-b6a9-2c5d8e9f1a04","reason":"expired"}
```

A failed command writes exactly one error line to stderr:

```json
{"error":{"code":"NO_CAPACITY","message":"No device capacity is currently available"}}
```

`code` is one of the codes in the [errors reference](/simlock/docs/reference/errors), or `USAGE` for a bad flag, a missing argument or an unknown command, or `INTERNAL` for anything unexpected. A usage message for an unknown command or a missing argument ends with ``(run `simlock --help` for usage)``.

### Durations

Flags that take a duration (`--ttl`, `--timeout`, `--since`) accept a whole number followed by `ms`, `s`, `m`, `h` or `d`, such as `90s`, `15m` or `2d`. A number with no unit is milliseconds. Anything else is a usage error.

### Exit codes

| Exit | Meaning |
| --- | --- |
| 0 | Success. |
| 1 | The command failed: an internal error, a lost or failed daemon connection, a refused credential, or another failure listed under 1 in the errors reference. |
| 2 | The request was wrong: a usage error, an invalid request, or a command this daemon does not run. |
| 10 | A deadline ran out: the queue wait, a passthrough command, or a download. |
| 11 | Busy: no capacity with `--no-wait`, or a device or component held by other work. Try again later. |
| 12 | What you asked for does not exist here or cannot be provided: a model, a runtime, a worker, a device. |
| 13 | You already hold a lease, or the lease ID is taken. |
| 14 | `lease` without `--detach`: the daemon ended the lease before you did. |
| 15 | `component install` with `--worker` or `--all-workers`: at least one worker did not install. |

`simlock simctl` and `simlock adb` exit with the tool's own exit code, which can collide with these numbers. Check stderr for an `{"error":...}` line, which only Simlock writes. The [errors reference](/simlock/docs/reference/errors#exit-codes) lists which error code gives which exit code.

## Environment variables

### Read by the CLI and the MCP server

| Variable | Meaning | Default |
| --- | --- | --- |
| `SIMLOCK_HOME` | The folder Simlock keeps everything in. The worker uses it directly; a gateway uses its `gateway` subfolder. A path so long that the daemon's socket path would pass the system limit fails with `USAGE` (exit 2). | `~/.simlock` |
| `SIMLOCK_ADMIN_TOKEN` | An admin credential: an operator token or the daemon's `admin.token` secret. Used when `--token` is not given. | Unset: the CLI reads `admin.token` |
| `SIMLOCK_AGENT_ID` | The requester identity. When set, it wins over the session variables below. | Unset |
| `CLAUDE_CODE_SESSION_ID` | Set by Claude Code. Gives the identity `claude-code:<id>`. | — |
| `CODEX_SESSION_ID` | Set by Codex. Gives the identity `codex:<id>`. | — |

### Requester identity

Simlock limits leases per requester (one by default), so each agent session needs one stable identity. The CLI uses the first of these:

1. `--agent-id <id>` on `simlock lease`.
2. `SIMLOCK_AGENT_ID`, when set.
3. `CLAUDE_CODE_SESSION_ID`, as `claude-code:<id>`, when set and not empty.
4. `CODEX_SESSION_ID`, as `codex:<id>`, when set and not empty.
5. An ID made from the process ID, different for every command.

Under Claude Code and Codex, every `simlock` command in one session is the same requester with no setup. `simlock mcp` resolves the same way, falling back to `mcp:<pid>`. Codex does not pass `CODEX_SESSION_ID` to an MCP server, so under Codex the MCP server and the CLI are two requesters and can hold two leases. Elsewhere, set a different `SIMLOCK_AGENT_ID` for each agent session; a single value shared by several agents makes them one requester with one lease.

### Read by a daemon the CLI starts

A daemon started on demand inherits the environment of the command that started it. Set these in that shell, or restart the daemon after you change them.

| Variable | Meaning |
| --- | --- |
| `ANDROID_HOME`, `ANDROID_SDK_ROOT` | Where the Android SDK is, tried in this order, then `~/Library/Android/sdk`. |
| `JAVA_HOME` | The JDK the Android SDK tools run on. |

### Set in a lease's environment

`simlock lease --export-env` prints these, and the JSON grant carries them under `environment`. Set them before you run the platform tool directly.

| Variable | When | Meaning |
| --- | --- | --- |
| `SIMLOCK_IOS_DEVICE_SET` | iOS simulator | The device set to pass to `xcrun simctl --set`. |
| `SIMLOCK_DEVICE_UDID` | Physical iOS device | The device's UDID. |
| `ANDROID_ADB_SERVER_PORT` | Android | The adb server that sees the device: Simlock's own server for an emulator, `5037` for a physical device. |
| `ANDROID_SERIAL` | Physical Android device | The device's adb serial. |
