---
title: How requests are routed
description: How the gateway picks a worker for a lease request, how requests wait in the fleet queue, and what an agent sees when no worker can serve a request.
---

When an agent asks the gateway for a device, one of three things happens:

- A worker can serve it now: the gateway sends the request there.
- Workers could serve it, but none can right now: the request waits in the fleet queue.
- No worker could ever serve it: the request fails at once.

## Which worker gets a request

A worker can take a request only when it:

- is connected, not drained, healthy, and has finished reporting its devices since it connected;
- has every optional capability the request needs (for example, a lease through the agent-device integration needs a worker with that integration turned on);
- offers the model or device class asked for, with a matching OS version already installed;
- holds a fresh copy of the baseline, when the request names one (see [Baselines through a gateway](/simlock/docs/gateway/managing-workers#baselines-through-a-gateway));
- slims every category in the request's `except` list and would give a slim device: the request's mode, or the baseline's, or else the worker's `ios.defaultMode` is `slim`;
- has no requests waiting in its own queue, for example from agents on that machine. This doesn't apply to physical devices.

Among those workers, the gateway prefers:

1. **A worker with a warm device.** A booted, unleased device that matches the request, including its slim or full mode, means the agent gets a device without waiting for a boot. For a request that names a baseline, only a copy of the baseline's current version counts.
2. **A worker with room to boot one.** It needs a free device slot, or a warm device it can shut down to make room. Workers whose new devices are not paused by host memory pressure come first (a worker that only paused warming still counts as calm), then workers under their RAM budget, then the worker with the most free device slots. A worker that paused new devices still gets the request when it has a warm match or when every worker is paused.

A request for a physical device goes only to a worker with a matching enrolled device that is free now. If none is free, the request waits.

A worker can still turn a request down, for example because an agent on that machine took the last free slot a moment earlier. The gateway then tries another worker, or puts the request back in the fleet queue.

## When every worker is busy: the fleet queue

A request that no worker can take now waits at the gateway, oldest first, or by the priority an [admission command](#ranking-or-refusing-requests-with-an-admission-command) gave it when one is set. Requests for virtual devices and for physical devices wait in separate lines. A request one worker can serve isn't held up by an older one that needs a different worker.

By default a request waits until a worker can take it. To give up after a while, pass `--timeout`:

```sh
simlock --gateway lease --platform ios --device "iPhone 16" --timeout 10m
```

When the time runs out, the request fails with `QUEUE_TIMEOUT` (exit 10). To fail at once instead of waiting, pass `--no-wait`; the request fails with `NO_CAPACITY` (exit 11) if no worker can take it now.

To see the queue, run `simlock --gateway status`, which prints `Queue depth`, or open the console's **Queue** page. It lists each waiting request and, for each worker, why that worker didn't take it. See [Fleet console](/simlock/docs/gateway/fleet-console#why-a-request-waits).

## Ranking or refusing requests with an admission command

Set `gateway.admission.command` on the gateway to an argv list, and the gateway runs it once for every new lease request, before the request waits:

```sh
simlock --gateway config set gateway.admission.command '["bun","/etc/simlock/policy.ts"]'
```

The gateway writes one line of JSON to the command's stdin and then closes it:

```json
{"requesterId":"job-78","principal":"tok_7f3a","platform":"ios","request":{"platform":"ios","leaseId":"job-78"},"metadata":{}}
```

`request` is the `lease.request` input as the caller sent it, without `requesterId` and `idempotencyKey`. It is not filled with defaults: a `ttlMs` the caller did not send is absent. `metadata` is `{}` for now.

The command exits 0 and prints one JSON object on stdout, optionally surrounded by whitespace:

| Output | The caller gets |
| --- | --- |
| `{"priority": 10}` | The request waits at priority 10. The priority is an integer from -1000 to 1000. |
| `{}` | The request waits at priority 0, the same as with no command. |
| `{"deny": "budget used"}` | `ADMISSION_DENIED` (exit 16, HTTP 403) with the reason, 1 to 500 characters. |
| Anything else | `ADMISSION_FAILED` (exit 16, HTTP 503). |

Any other key in the object is ignored. Within a line, a higher priority is served first, and requests of equal priority are served oldest first. The virtual and the physical line are ordered apart.

The gateway fails closed. These each refuse the request with `ADMISSION_FAILED`, and the gateway log says why at warn level, with the first 2048 bytes of the command's stderr:

- a non-zero exit, or a kill by a signal;
- no exit within `gateway.admission.timeoutMs` (5 seconds by default), counted from the start; the command is killed;
- more than 65536 bytes on stdout; the command is killed;
- output that is not a priority, `{}` or a refusal (not JSON, two objects, a priority out of range, an empty reason, both keys);
- a program that does not exist or cannot start.

A request the gateway already holds (a repeated idempotency key), a requester over its limit and a chosen lease id that is taken or ended are answered without running the command. A `lease.cancel` for the requester while the command runs kills the command and ends the request `cancelled`. A worker ignores `gateway.admission.*`.

## When no worker can serve a request

The gateway doesn't queue a request that no worker could serve. It fails at once, with the same code a single worker would give:

| Code | Exit | HTTP | Why | What to do |
| --- | --- | --- | --- | --- |
| `NO_CAPACITY` | 11 | 503 | Workers could serve it, but none is connected and taking requests: they are all disconnected, drained or incompatible. | Bring a worker back, or undrain one. |
| `NO_DRIVER` | 12 | 422 | No worker supports the platform, for example no worker has Android tools. | Add a worker that has the platform. |
| `UNKNOWN_MODEL` | 12 | 422 | No worker offers that model or device class, or, for a physical device, no worker has one enrolled. | Check the name with `simlock --gateway catalog`. |
| `RUNTIME_MISSING` | 12 | 422 | Workers offer the model, but none has a matching OS version installed. The gateway never downloads one. | Install it on the workers. See [Install runtimes and images on workers](/simlock/docs/gateway/managing-workers#install-runtimes-and-images-on-workers). |
| `CAPABILITY_MISSING` | 12 | 422 | No worker that could serve the request has the optional capability it needs turned on. | Turn the capability on for a worker. |
| `BAD_REQUEST` | 2 | 400 | The request names `except` categories, and no worker slims all of them, or none would give a slim device (every worker's default mode is `full` and the request names no mode, or the baseline is `full`). | Name categories the workers slim (`ios.slim.categories`), pass `--mode slim`, or set `ios.defaultMode` to `slim`. |
| `UNKNOWN_BASELINE` | 12 | 404 | No worker holds the baseline the request names. | List the baselines with `simlock --gateway baseline list`. |
| `BASELINE_MISMATCH` | 2 | 422 | Every worker that holds the baseline has a copy that differs from a platform, model, OS, mode or image tag the request names. The message is from the first worker, by worker id. | Drop the field, or change it to the baseline's own value. |
| `BASELINE_STALE` | 12 | 422 | Every copy that fits the request is stale, for example its runtime is no longer installed. The message gives the first worker's reason. | Fix what the reason names, or save the baseline again. |

The gateway checks this again while a request waits. If the last worker that could serve a waiting request disconnects or is drained, even for a moment, the request fails with `NO_CAPACITY` instead of waiting for the worker to come back.

If a worker starts to create a device for the request and fails, the request fails with that worker's error. If every worker that could serve the request fails to create the device, it fails with `PROVISION_FAILED` (exit 1).

All codes are in the [Error reference](/simlock/docs/reference/errors).

## The lease limit across the fleet

A requester holds at most `lease.maxPerRequester` leases through the gateway (1 by default), counted across all workers. When the limit is set per platform, each platform counts on its own. A request over the limit fails with `REQUESTER_ALREADY_LEASED` (exit 13).

A lease on a disconnected worker stops counting once its time to live has run out, since nobody can have renewed it through the gateway.

## Drained workers

A drained worker gets no new requests from the gateway. Its leases keep running, and agents can renew and release them as usual. Agents on the worker machine itself can still lease its devices. See [Take a worker out of service](/simlock/docs/gateway/managing-workers#take-a-worker-out-of-service).

## When the gateway restarts

The gateway keeps waiting requests in memory only. When it stops or restarts:

- **Waiting requests are lost.** An agent waiting with `simlock --gateway lease` gets `DAEMON_CONNECTION_LOST`. Over HTTP, the request's id answers `404`, and sending the same `Idempotency-Key` again starts a new request. Ask again.
- **Granted leases survive.** They live on the workers, and the devices stay booted. While the gateway is down, nothing can renew, release or run commands on them through it, so a lease whose time to live runs out meanwhile expires. When the gateway is back, these leases work through it again. In the first minute after a start, a renew, release or command on a lease whose worker has not yet reported answers `WORKER_UNREACHABLE`, which clients retry; the lease stays.
- **Drained workers stay drained.**

A lease ID you chose that you send again after its lease ended gets `LEASE_ENDED`, not a new device, for `lease.endedIdRetentionMs` (24 hours by default). A gateway refuses it itself when a worker reported the end, even across a gateway restart. A lease that ended while the gateway was down is not recorded by the gateway: the request goes to a worker, and the worker that held the lease answers `LEASE_ENDED` (a request routed to another worker is granted).

Because of the lease limit, a request sent again after a restart may get `REQUESTER_ALREADY_LEASED`, naming the lease the requester already holds. Use that lease or release it.

If a worker's connection drops while it grants a lease, the agent gets `WORKER_UNREACHABLE`, but the worker may have granted the lease anyway. That lease runs on the worker until its time to live runs out.
