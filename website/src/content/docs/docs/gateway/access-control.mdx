Every agent, person and worker that reaches a gateway or a worker over HTTP needs a token made on that daemon, or a sign-in through a sign-in proxy you set up. On the daemon's own machine, the CLI needs no token to lease devices, and as the user who runs the daemon it has admin rights with no setup.

The examples use the gateway. Tokens work the same way on a worker: drop `--gateway`.

## Pick a token role

| Role | Made for | May |
| --- | --- | --- |
| `agent` | A coding agent that leases devices over HTTP. | Read the catalog and status (only its own leases and waiting requests), list installed runtimes, request, renew and release its own leases, cancel its own waiting requests, run commands on the devices it leases, watch the screen of its own leases (see [Watching the screen](/simlock/docs/using-devices/watching-the-screen#stream-from-your-own-tool)), and open the input socket of its own leases (see [Watching the screen](/simlock/docs/using-devices/watching-the-screen#send-input-to-your-own-lease)). |
| `operator` | A person, or a script that manages the fleet. | Everything an agent may, for every requester's leases, plus the console, events, usage figures, tokens, worker commands and component installs. |
| `worker` | A worker machine joining a gateway. | Connect one worker to the gateway, and nothing else. The first worker that joins with it keeps it; another worker with the same token, and any other request with it, is refused with `403`. |

A valid token used for something its role may not do gets `403 FORBIDDEN`. An unknown or revoked token gets `401 UNAUTHENTICATED`.

A token works only on the daemon that made it. A gateway token doesn't work on a worker, and a worker's tokens don't work on the gateway.

### Give each agent its own token

Over HTTP, the token is the requester. Every lease and request made with one agent token belongs to the same requester, and a requester holds one lease at a time by default (one per platform when the operator sets `lease.maxPerRequester` per platform). Two agents sharing a token block each other. Give every agent its own token, with a label you will recognise in the console.

### An agent token gives access to the worker machine

<Aside type="caution">
Treat an agent token like shell access to your workers. Commands an agent runs on its device, such as `adb pull` or `simctl` commands, run on the worker as the user who runs the worker daemon, and can read and write any file that user can. `simctl spawn` alone starts any program on the worker. Through a gateway, the command runs on the worker that holds the lease. Give an agent token only to something you would let run commands on your workers.

A command gets only a short, fixed list of the daemon's environment variables (see [Running commands with exec](/simlock/docs/using-devices/remote-agents#running-commands-with-exec)). That doesn't keep a secret safe: the command runs as the same user as the daemon, so it can still read the daemon's environment and files.
</Aside>

## Make, list and revoke tokens

Make a token. `--label` is optional, and shows wherever the token's leases are listed:

```sh
simlock --gateway token create --role agent --label ci-ios-runner-3
```

```json
{"secret":"slk_Xr8vB2nQ5kLw0pT7yHc4mZs9dFj1gUe6aKo3iVb-Rq0","token":{"id":"tok_5e2b8d1c-4a7f-4c9e-b3d6-0f1a2c8e7b45","role":"agent","label":"ci-ios-runner-3","createdAt":1792569600000}}
```

The `secret` is printed once and can't be shown again. If you lose it, make a new token and revoke the old one.

List tokens. The list shows ids, roles and labels, never secrets. A worker token that a worker has joined with also shows `workerId`, the id of the worker it is paired with:

```sh
simlock --gateway token list
```

```json
{"tokens":[{"id":"tok_3f9c2a1e-7b4d-4e8a-9c61-2d5f0b7a8e14","role":"operator","label":"alex-laptop","createdAt":1792569600000},{"id":"tok_5e2b8d1c-4a7f-4c9e-b3d6-0f1a2c8e7b45","role":"agent","label":"ci-ios-runner-3","createdAt":1792569600000}]}
```

Revoke a token by its id:

```sh
simlock --gateway token revoke tok_5e2b8d1c-4a7f-4c9e-b3d6-0f1a2c8e7b45
```

```json
{"revoked":true}
```

A revoked token stops working on its next request. Revoking a worker token also closes that worker's connection, and lets the worker join with a new token. Leases made with a revoked agent token stay until their time to live runs out or an operator releases them; the agent can no longer renew or release them. An id that names no token answers `"revoked":false`.

## Admin commands on the CLI

The CLI talks to the daemon on its own machine. Without admin rights it connects as an agent: it can lease, but admin commands such as `token create`, `worker drain` or `config get` fail with `FORBIDDEN`.

For admin rights, the CLI uses the first of these it finds:

1. `--token <secret>` on the command line.
2. The `SIMLOCK_ADMIN_TOKEN` environment variable.
3. The `admin.token` file in the daemon's folder: `~/.simlock/gateway/admin.token` for the gateway, `~/.simlock/admin.token` for the worker.

The daemon writes a new `admin.token` each time it starts, readable only by the user who runs it. So as that user on that machine, admin commands work with no setup. As any other user, pass an operator token's secret with `--token` or `SIMLOCK_ADMIN_TOKEN`.

When the CLI finds none of these, or the daemon refuses it, the CLI goes on as an agent and prints this line on stderr:

```json
{"notice":"admin credential unavailable; connecting as agent (admin-only commands will fail with FORBIDDEN)"}
```

A rejected `admin.token` usually means the daemon restarted while the command was starting. Run the command again.

## Sign in to the console through a sign-in proxy

If your company signs people in through a proxy such as Cloudflare Access, the gateway can trust it. A person the proxy signed in opens the console with no token, and the sidebar shows their name.

<Aside type="caution">
Every person the proxy signs in becomes an operator, with full rights on the gateway and, through it, on every worker. Restrict who may pass the proxy to the people you would give an operator token.
</Aside>

The proxy must add a signed JWT to each request and publish its public keys. Simlock accepts a JWT only when its signature, issuer, audience and time window check out, and it carries a `sub` (1 to 120 characters) and an `email`. The console shows the JWT's `name`, or the email when there is no name.

Set all four required keys in one command: Simlock checks the whole setting on each `config set`. This example is for Cloudflare Access with the team name `acme`:

```sh
simlock --gateway config set http.proxyAuth '{"header":"cf-access-jwt-assertion","jwksUrl":"https://acme.cloudflareaccess.com/cdn-cgi/access/certs","issuer":"https://acme.cloudflareaccess.com","audience":"4f1c2b9e7d3a8c6f5e0b1d2a9c8e7f6b5a4d3c2b1e0f9a8d7c6b5a4f3e2d1c0b","signOutUrl":"https://acme.cloudflareaccess.com/cdn-cgi/access/logout"}'
```

Then restart the gateway.

| Key | What it is |
| --- | --- |
| `header` | The request header that carries the proxy's JWT. Matched without regard to case. |
| `jwksUrl` | Where the proxy publishes its public keys. It must be `https://`, or `http://` on `localhost`, `127.0.0.1` or `::1`. |
| `issuer` | The `iss` the JWT must carry. |
| `audience` | The `aud` the JWT must carry. For Cloudflare Access, the application's audience tag. |
| `signOutUrl` | Optional. Where the console's **Sign out** sends a person signed in through the proxy. Without it, such a person sees no **Sign out**. |

Your proxy must also:

- **Let workers through without a sign-in.** Workers connect to `/v1/uplink` with their join token, not a proxy sign-in. The other way is to give each worker the proxy's service credentials in [`gateway.headers`](../../reference/configuration/); the worker sends them on its connection.
- **Let `/v1/healthz` through**, if anything checks the gateway's health.
- **Let agents through**, by whatever means your proxy offers, such as a bypass rule or service credentials. Agents send their Simlock token, which Simlock checks as usual. When a request carries both a Simlock token and a JWT, the token wins.
- **Serve the console over HTTPS.** Over plain `http://` from another machine, a person signed in through the proxy can look but not change anything: Simlock refuses their changes and screen input.

An operator token pasted into the console still works behind the proxy.

### When the console refuses the proxy's sign-in

The console shows the token form with a line such as "Your sign-in proxy's identity was refused: it has expired. You can still sign in with an operator token." The gateway's log names the reason as a code, and an HTTP client gets it as `reason` in the `401` answer.

| The console says it | Reason | What to check |
| --- | --- | --- |
| has expired | `expired` | The JWT expired more than 60 seconds ago. Sign in to the proxy again. |
| is not valid yet | `not-yet-valid` | The gateway machine's clock. |
| comes from a different sign-in service | `wrong-issuer` | `issuer` matches the JWT's `iss`. |
| was made for a different application | `wrong-audience` | `audience` matches the JWT's `aud`. |
| is signed in a way this daemon does not accept | `algorithm` | The proxy signs with RS256 or ES256. |
| its signature does not check out | `unknown-key` or `bad-signature` | `jwksUrl` is the proxy's own key URL. |
| this daemon cannot reach the sign-in service's keys | `keys-unavailable` | The gateway can reach `jwksUrl`. This shows once the keys have been out of reach for 10 minutes. |
| is not a valid sign-in token | `malformed` | `header` names the header that holds the JWT. A JWT over 8 KiB, with no expiry, or with a `sub` over 120 characters is refused too. |

The console's sign-in, sign-out and token handling are described in [Web console](/simlock/docs/worker/console).
