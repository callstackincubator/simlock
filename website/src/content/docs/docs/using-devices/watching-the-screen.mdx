The console can show the live screen of any running device, leased or not: an iOS simulator, an Android emulator, a physical Android phone, or a physical iPhone. You watch; you cannot tap or type in the console. A coding agent can also watch its own lease's screen over HTTP (see [Stream from your own tool](#stream-from-your-own-tool)), and open an input socket for it (see [Send input to your own lease](#send-input-to-your-own-lease)). Nothing is captured until someone opens a device's **Screen** tab, and the capture stops when they leave the tab, close the drawer, or the device stops running.

## Before you start

- The console is on, and you can sign in with an operator token. See [Console](/simlock/docs/worker/console).
- Screen streaming is turned on for the worker that holds the device. It is off by default.
- For a physical iPhone: the worker runs Xcode 27 or later, and the iPhone runs iOS 27 or later.

## Turn screen streaming on

<Steps>

1. On each worker, turn streaming on:

   ```sh
   simlock config set capabilities.stream.enabled true
   ```

2. With a gateway, turn it on there too. The gateway passes each stream through to the worker that holds the device:

   ```sh
   simlock --gateway config set capabilities.stream.enabled true
   ```

3. Restart each daemon you changed, because the setting is read when the daemon starts:

   ```sh
   simlock daemon stop
   simlock daemon start
   ```

4. Check that it is on. `simlock worker list` (with `--gateway` for a fleet) ends each worker's line with the stream's state:

   ```text
   3f81a2c4-9b7d-4e21-8a55-1c0e6f2d7b93 (mac-studio-2): connected -- ios 1/6, android 0/4, 1 lease(s) -- macOS 26.0 arm64; xcode 26.1 (17B55) -- stream available
   ```

   `stream unavailable: <reason>` says why no platform on that worker can stream. `stream off` means the setting is not on there.

</Steps>

To turn streaming off, set `capabilities.stream.enabled` to `false` and restart the daemon.

## Watch a device

<Steps>

1. Open the console and go to **Fleet**, then select the worker. On a gateway, select the worker that holds the device.
2. Select the device.
3. Open the **Screen** tab.

</Steps>

The picture starts by itself. The **Stream details** button (ⓘ) shows its size, codec, frame rate and bandwidth. Leaving the tab, closing the drawer, leaving the page and signing out stop it. A lease being taken on the device while you watch does not interrupt the picture.

A device that is not running has no picture, and the tab says why: shut down, starting, being reset, quarantined, not connected. The picture starts by itself once the device is `ready` again. When streaming is off on the device's worker, the tab says "Streaming is off on" and the worker's name. When the worker cannot capture this device, the tab says why.

## What to expect

- **The first picture can take a while.** A simulator usually shows within seconds. A physical Android phone takes longer: Simlock checks the phone's screen and adb server before it starts. The console waits up to 200 seconds.
- **A phone with its screen off is woken first.** If it does not wake, you are told to turn it on. While a phone streams, it is kept awake as long as it is charging, and its setting is put back when the stream ends.
- **The picture ends with the device's run.** When the device is shut down, loses its connection, is quarantined or deleted, or its lease is released, expires or loses it, the stream stops, so a device is never watched after it is handed back or reset. When a lease ends it, the tab says "The lease was released.", "The lease expired.", "The lease was ended by an operator." or "The device was lost." Other ends show no such reason.
- **A frozen device does not look live.** A stream that gets no frames for 30 seconds ends with an error.
- **Each viewer is a separate capture.** Two browser tabs on one device capture it twice.
- **A rotated iOS simulator or iPhone keeps the first picture's scale.** An Android device's picture follows the rotation.

## Physical iPhone requirements

A physical iPhone streams only when both of these hold:

- The worker it is plugged into runs Xcode 27 or later.
- The iPhone runs iOS 27 or later.

Otherwise the panel shows the reason, for example:

```text
Physical iPhone streams need iOS 27 or later on the iPhone; 00008110-001A2B3C4D5E801E runs iOS 18.6. Update the iPhone and ask for the stream again.
```

Simulators stream on any Xcode the worker supports.

## Quality and cost

The worker encodes the screen as H.264. Three settings on the worker trade picture quality for bandwidth:

| Setting | Default | What it does |
| --- | --- | --- |
| `capabilities.stream.maxDimension` | `720` | Longest side of the picture, in pixels (96 to 4096). Costs the most bandwidth. |
| `capabilities.stream.bitrateKbps` | `1500` | Target bitrate, in kilobits per second (100 to 40000). |
| `capabilities.stream.fps` | `30` | Highest frame rate (1 to 60). A still screen sends far fewer frames. |

At the defaults, a screen that is busy redrawing costs about 1.4 Mbit/s, and a screen nobody touches costs between 25 and 90 kbit/s. Each iOS capture uses about 50 to 80 MB of memory on the worker. Restart the daemon after you change these.

## Stream from your own tool

Anything with an operator token can read the screen of a running device, leased or not, over HTTP at `GET /v1/stream/workers/<worker-id>/devices/<device-id>`, on a worker (which answers only for its own id) or on a gateway (which relays to the named worker), with streaming on. A device streams while it is `ready` or `leased`; any other state answers 409 `DEVICE_NOT_RUNNING`. The stream ends when the device stops running or its lease ends. An agent token cannot read a device's screen by device.

A lease's holder can read its own lease's screen at `GET /v1/leases/<lease-id>/stream`, on a worker or on a gateway, with the same frames. An operator token can read any lease's. A lease that is not the caller's, or does not exist, answers 404 `UNKNOWN_LEASE`. With streaming off on the daemon that answers, the path is a plain 404; through a gateway, streaming must be on for the lease's worker too, or the answer is 503 `STREAM_UNAVAILABLE`.

The body is Simlock's own framing of H.264 frames, made for the console's player, and it runs until you close the request. When a lease end stops a stream, its last frame has tag `0x07` and holds JSON like `{"reason":"explicit"}`, then the body ends. The reason is `explicit` (released), `expired`, `killed` (ended by an operator) or `device-lost`. Any other end sends no such frame. Most users watch in the console instead.

## Send input to your own lease

A lease's holder can open a WebSocket for its lease at `GET /v1/leases/<lease-id>/input` (with an `Upgrade: websocket` request), on a worker or on a gateway, with its agent token in an `Authorization: Bearer` header. An operator token can open any lease's. Turn it on with `capabilities.input.enabled` (off by default; see [Configuration reference](/simlock/docs/reference/configuration)); through a gateway, the gateway and the lease's worker both need it on.

The messages are expo serve-sim's: each is one tag byte and UTF-8 JSON, so a client that already drives serve-sim (T3 Code's device panel) needs nothing Simlock-specific. The server sends `0x83` (input is accepted from now on), then `0x82` with the screen as it is now, `{"width":1179,"height":2556,"orientation":"portrait"}`, and again whenever the size changes. A device that takes no input gets `0x82` `{"width":1,"height":1,"orientation":"portrait","inputUnavailable":true}`, and the socket stays open. An Android emulator, an enrolled Android phone and an iOS simulator take input (see below); a physical iPhone does not, so its sockets get that answer.

The client sends `0x03` touch (`{"type":"begin","x":0.4,"y":0.7}`, `type` is `begin`, `move` or `end`, positions are fractions from 0 to 1), `0x04` button (`home`, `app_switcher`, `lock` or `back`), `0x06` key (`{"type":"down","usage":4}`, a USB HID usage from 0 to 255) and `0x0b` scroll. A message that is not valid JSON, has an unknown tag, a position outside 0 to 1, or is over 64 KiB is dropped and the socket stays open. `0x07` (orientation) is always dropped. `0x10` is answered `0x90` `{"requestId":7,"ok":false}`.

On Android, a tap, swipe, scroll, key or button reaches the device through a second, control-only scrcpy server that Simlock starts for the lease; it shows no picture and changes no device setting. Taps and scrolls land on the screen as it is now, in its current rotation, and Simlock reads the size every 2 seconds, so after an agent rotates the device a tap may use the old size for up to 2 seconds, and the socket then gets a new `0x82`. A scroll sends 1 wheel unit for each 1/16 of the screen, up to 16, at the given position or the screen's centre; a positive `dy` moves the content down and a positive `dx` moves it right. `home`, `app_switcher`, `lock` and `back` are Android's Home, Recents, Power and Back keys. A `0x06` key is a USB HID usage typed as a US keyboard: letters, digits, Enter, Escape, Backspace, Tab, Space, the punctuation row, the arrows and the modifiers (Shift, Ctrl, Alt, Meta) work, and a modifier stays held for the keys after it until its `up`; other usages (function keys, the keypad) are dropped. A dark phone screen is not woken, so a tap on it does nothing. A phone whose adb check is closed gets `inputUnavailable`.

On an iOS simulator, a tap, swipe, scroll and `home` work, and so do `0x06` keys on iOS 26 and older runtimes. A tap reaches the simulator through a helper process that Simlock starts for the lease; it shows no picture. `home` brings the home screen forward and sends the app to the background. A scroll is sent as a finger drag. `app_switcher`, `lock` and `back` are dropped, and rotation is not supported. On an iOS 27 or newer runtime the simulator ignores injected keys, so `0x06` keys are dropped and the `0x82` message carries `"keyboardUnavailable":true`. The `0x82` message always says `"orientation":"portrait"`.

Up to 8 sockets share one lease's device input. The socket closes with:

| Code | Reason | When |
| --- | --- | --- |
| 4001 | `explicit`, `killed`, `expired` or `device-lost` | The lease ended. Through a gateway, `lease ended` if the worker did not say why within 2 seconds. |
| 1011 | `Worker <id> stopped answering` | Through a gateway, the worker stopped answering for 15 seconds or its uplink dropped. |
| 1001 | `Simlock is stopping` | The daemon is stopping. |
| 1013 | `Input is unavailable for this lease` | A 9th socket, a device input that failed, or a reconnect within 10 seconds of a failed open. |

A socket that answers no ping within 15 seconds is closed. A lease that is not the caller's, or does not exist, answers 404 `UNKNOWN_LEASE`, no token answers 401, and a plain `GET` without an upgrade answers 426. With input off on the daemon that answers, the path is a plain 404. Through a gateway, a worker with input off answers 503 `INPUT_UNAVAILABLE` ("Worker w1 does not take input for lease L-42; turn on capabilities.input.enabled there"), and a worker that gives no answer within 10 seconds answers 503 `WORKER_UNREACHABLE`.

## When it does not work

| What you see | Why | What to do |
| --- | --- | --- |
| "Streaming is off on mac-studio-2." | `capabilities.stream.enabled` is not `true` on that worker. | Turn it on and restart the worker's daemon. |
| The panel says the screen cannot be captured, naming iOS 27 or Xcode 27 | A physical iPhone below iOS 27, or a worker on an Xcode older than 27. | Update the iPhone or the worker's Xcode. |
| "The phone's screen is off and did not turn on." | The phone did not wake. | Unlock the phone, then leave the **Screen** tab and open it again. |
| The tab gives up waiting for the first picture | The device painted nothing for 30 seconds. | Leave the **Screen** tab and open it again. |
| The picture stops on a device that is still running | The device stopped sending frames. | Leave the **Screen** tab and open it again. |
