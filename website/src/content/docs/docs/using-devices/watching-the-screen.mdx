The console can show the live screen of any running device, leased or not: an iOS simulator, an Android emulator, a physical Android phone or a physical iPhone. In the console you can only watch; you can't tap or type.

Your own tools can do more over HTTP: [stream a lease's screen](#stream-from-your-own-tool) and [send it taps and keys](#send-input-to-your-own-lease).

Nothing is captured until someone opens a device's streaming page. Capture stops when they select **Stop watching**, leave the page, or the device stops running.

## Before you start

- The console is on, and you can sign in with an operator token. See [Console](/simlock/docs/worker/console).
- Screen streaming is on for the worker that holds the device. It is off by default.
- For a physical iPhone: the worker runs Xcode 27 or later, and the iPhone runs iOS 27 or later.

## Turn screen streaming on

<Steps>

1. On each worker, turn streaming on:

   ```sh
   simlock config set capabilities.stream.enabled true
   ```

2. With a gateway, turn it on there too:

   ```sh
   simlock --gateway config set capabilities.stream.enabled true
   ```

3. Restart each daemon you changed. The setting is only read when the daemon starts:

   ```sh
   simlock daemon stop
   simlock daemon start
   ```

4. Check that it is on. `simlock worker list` (with `--gateway` for a fleet) ends each worker's line with the stream's state:

   ```text
   3f81a2c4-9b7d-4e21-8a55-1c0e6f2d7b93 (mac-studio-2): connected -- ios 1/6, android 0/4, 1 lease(s) -- macOS 26.0 arm64; xcode 26.1 (17B55) -- stream available
   ```

   - `stream available`: it works.
   - `stream off`: the setting isn't on for that worker.
   - `stream unavailable: <reason>`: no platform on that worker can stream, and why.

</Steps>

To turn streaming off, set `capabilities.stream.enabled` to `false` and restart the daemon.

## Watch a device

<Steps>

1. Open the console, go to **Fleet** and select the worker that holds the device.
2. Select the device.
3. Select **Watch** in the drawer.

</Steps>

The picture starts by itself. Two pills over the picture show its frame rate, codec, size and bandwidth. Someone taking a lease on the device while you watch doesn't interrupt the picture.

A device that isn't running has no picture, and the page says why: shut down, starting, being reset, quarantined or not connected. The picture starts by itself once the device is `ready` again.

## What to expect

- **The first picture can take a while.** A simulator usually shows within seconds. A physical Android phone takes longer. The console waits up to 200 seconds.
- **A phone with its screen off is woken first.** If it doesn't wake, you are told to turn it on. While a phone streams and is charging, it is kept awake. Its setting is put back when the stream ends.
- **The picture ends when the device stops or is handed back.** When the device shuts down, loses its connection, is quarantined or deleted, or its lease ends, the stream stops. So nobody can watch a device after it is handed back or reset. When a lease end stops it, the page says why: "The lease was released.", "The lease expired.", "The lease was ended by an operator." or "The device was lost."
- **A dropped stream reconnects.** If the picture started and the stream then ends without a reason, such as when your sign-in through a proxy expires, the page opens it again.
- **A frozen device doesn't look live.** A stream that gets no new frames for 30 seconds ends with an error.
- **Each viewer is a separate capture.** Two browser tabs on one device capture it twice.
- **Rotation.** A rotated iOS simulator keeps the scale of the first picture. An Android device's picture follows the rotation, and so does an iPhone's: a new meta frame gives the new size, and nobody has run it on a physical iPhone yet.
- **Foldables.** An iPhone Duo simulator shows the panel in use, upright, and the open stream switches panels about a second after the device folds or unfolds, with no reconnect. A stream opened while the screen is all black can show the cover for a few seconds before it switches. If SpringBoard's log never names the move, the stream stays on the panel it opened on.
- **The size can change.** The size headers give the picture's size when the stream opens; a meta frame in the body gives each later size. A viewer that reads the size once draws a stretched picture after a fold until it reconnects.

## When it doesn't work

| What you see | Why | What to do |
| --- | --- | --- |
| "Streaming is off on mac-studio-2." | `capabilities.stream.enabled` isn't `true` on that worker. | Turn it on and restart the worker's daemon. |
| The panel says the screen can't be captured, naming iOS 27 or Xcode 27 | A physical iPhone below iOS 27, or a worker on Xcode older than 27. | Update the iPhone or the worker's Xcode. |
| "The phone's screen is off and did not turn on." | The phone didn't wake. | Unlock the phone, then select **Stop watching** and **Watch** again. |
| The page gives up waiting for the first picture | The device showed nothing for 30 seconds. | Select **Stop watching**, then **Watch** again. |
| The picture stops on a device that is still running | The device stopped sending frames. | Select **Stop watching**, then **Watch** again. |

A physical iPhone that can't stream says why in the panel, for example:

```text
Physical iPhone streams need iOS 27 or later on the iPhone; 00008110-001A2B3C4D5E801E runs iOS 18.6. Update the iPhone and ask for the stream again.
```

Simulators stream on any Xcode the worker supports.

## Picture quality and bandwidth

Three settings on the worker trade picture quality for bandwidth. Restart the daemon after you change them.

| Setting | Default | What it does |
| --- | --- | --- |
| `capabilities.stream.maxDimension` | `720` | Longest side of the picture, in pixels (96 to 4096). Has the biggest effect on bandwidth. |
| `capabilities.stream.bitrateKbps` | `1500` | Target bitrate, in kilobits per second (100 to 40000). |
| `capabilities.stream.fps` | `30` | Highest frame rate (1 to 60). A still screen sends far fewer frames. |

At the defaults, a busy screen uses about 1.4 Mbit/s, and a screen nobody touches uses 25 to 90 kbit/s. Each iOS capture uses about 50 to 80 MB of memory on the worker.

## Stream from your own tool

Most people watch in the console. This section is for building your own viewer. Streaming must be on (see above).

| Who | Route | Works on |
| --- | --- | --- |
| A lease's holder (or an operator, for any lease) | `GET /v1/leases/<lease-id>/stream` | A worker or a gateway |
| An operator, for any running device | `GET /v1/stream/workers/<worker-id>/devices/<device-id>` | A worker (its own id only) or a gateway |

An agent token can't read a device's screen by device id, only through its own lease.

What the routes answer:

- A device streams while it is `ready` or `leased`. In any other state, the device route answers `409 DEVICE_NOT_RUNNING`.
- A lease that isn't yours, or doesn't exist, answers `404 UNKNOWN_LEASE`.
- With streaming off on the daemon you call, the route answers a plain `404`. Through a gateway, streaming must also be on for the lease's worker, or the answer is `503 STREAM_UNAVAILABLE`.

The body is H.264 frames in Simlock's own framing, made for the console's player. It runs until you close the request, or until the device stops or its lease ends. When a lease end stops the stream, the last frame has tag `0x07` and holds JSON like `{"reason":"explicit"}`, then the body ends. The reason is `explicit` (released), `expired`, `killed` (ended by an operator) or `device-lost`. Other ends send no such frame.

## Send input to your own lease

A lease's holder can send taps, swipes, keys and buttons to its device over a WebSocket. An operator can do it for any lease.

**Turn it on** with `capabilities.input.enabled` on the worker (it is off by default; see [Configuration reference](/simlock/docs/reference/configuration)). Through a gateway, turn it on at the gateway and at the lease's worker.

**Connect** to `GET /v1/leases/<lease-id>/input` with an `Upgrade: websocket` request and your token in an `Authorization: Bearer` header, on the worker or the gateway.

Which devices take input:

- An iOS simulator, an Android emulator and an enrolled Android phone take input.
- A physical iPhone doesn't. Its socket stays open but reports `inputUnavailable` (see below).

### The messages

The messages use expo serve-sim's format, so a client that already drives serve-sim (such as T3 Code's device panel) needs nothing Simlock-specific. Each message is one tag byte followed by UTF-8 JSON.

From the server:

| Tag | Means |
| --- | --- |
| `0x83` | Input is accepted from now on. |
| `0x82` | The screen's size, such as `{"width":1179,"height":2556,"orientation":"portrait"}`. Sent after `0x83`, and again whenever the size changes. A device that takes no input gets `{"width":1,"height":1,"orientation":"portrait","inputUnavailable":true}`. |
| `0x90` | The answer to `0x10`: `{"requestId":7,"ok":false}`. |

From your client:

| Tag | Sends | Example |
| --- | --- | --- |
| `0x03` | Touch. `type` is `begin`, `move` or `end`; positions are fractions of the screen, from 0 to 1. | `{"type":"begin","x":0.4,"y":0.7}` |
| `0x04` | Button: `home`, `app_switcher`, `lock` or `back`. | |
| `0x06` | Key, as a USB HID usage from 0 to 255. | `{"type":"down","usage":4}` |
| `0x07` | Orientation: `portrait`, `portrait_upside_down`, `landscape_left` or `landscape_right`. | `{"orientation":"landscape_left"}` |
| `0x0b` | Scroll. | |

A message is dropped, and the socket stays open, when it isn't valid JSON, has an unknown tag, has a position outside 0 to 1 or an unknown orientation, or is over 64 KiB.

### On Android

- **Taps and scrolls** land on the screen as it is now, in its current rotation. Right after the device rotates, a tap may use the old screen size for up to 2 seconds; the socket then gets a new `0x82`.
- **A scroll** moves 1 wheel unit for each 1/16 of the screen, up to 16, at the given position or the screen's centre. A positive `dy` moves the content down; a positive `dx` moves it right.
- **Buttons**: `home`, `app_switcher`, `lock` and `back` are Android's Home, Recents, Power and Back.
- **Keys** are typed as a US keyboard. Letters, digits, Enter, Escape, Backspace, Tab, Space, the punctuation row, the arrows and the modifiers (Shift, Ctrl, Alt, Meta) work. A modifier stays held for the keys after it until its `up`. Other keys, such as function keys and the keypad, are dropped.
- **Orientation (`0x07`)** is dropped. Rotate an Android device with agent-device.
- **A dark screen isn't woken**, so a tap on it does nothing.
- Input on Android doesn't change any device setting.
- A phone whose adb check is closed reports `inputUnavailable`.

### On an iOS simulator

- **Taps, swipes and scrolls** work. A scroll is sent as a finger drag.
- **`home`** brings the home screen forward and sends the app to the background. `app_switcher`, `lock` and `back` are dropped.
- **Keys** work on iOS 26 and older. On iOS 27 and newer the simulator ignores injected keys, so they are dropped, and `0x82` carries `"keyboardUnavailable":true`.
- **Orientation (`0x07`)** turns the simulator as if you turned the phone in your hand. A screen that doesn't rotate, such as the iPhone home screen, stays as it is, and nothing tells the client.
- `0x82` always says `"orientation":"portrait"`, even after a rotation, and touch positions stay fractions of the screen in portrait.

### When the socket closes

Up to 8 sockets can share one lease's input.

| Code | Reason | When |
| --- | --- | --- |
| 4001 | `explicit`, `killed`, `expired` or `device-lost` | The lease ended. Through a gateway, `lease ended` if the worker didn't say why within 2 seconds. |
| 1011 | `Worker <id> stopped answering` | Through a gateway, the worker stopped answering for 15 seconds or lost its connection. |
| 1001 | `Simlock is stopping` | The daemon is stopping. |
| 1013 | `Input is unavailable for this lease` | A 9th socket, a failure to reach the device's input, or a reconnect within 10 seconds of a failed open. |

A socket that doesn't answer a ping within 15 seconds is closed.

Errors before the socket opens:

| Answer | Why |
| --- | --- |
| `401` | No token. |
| `404 UNKNOWN_LEASE` | The lease isn't yours, or doesn't exist. |
| `404` | Input is off on the daemon you called. |
| `426` | A plain `GET` without an upgrade. |
| `503 INPUT_UNAVAILABLE` | Through a gateway, input is off on the lease's worker ("Worker w1 does not take input for lease L-42; turn on capabilities.input.enabled there"). |
| `503 WORKER_UNREACHABLE` | Through a gateway, the worker didn't answer within 10 seconds. |

### Rotate without a socket

A lease's holder can rotate an iPhone or iPad simulator with one HTTP call, on a worker or a gateway. This works whether or not `capabilities.input.enabled` is on. The example uses the variables from [Remote agents](/simlock/docs/using-devices/remote-agents#lease-a-device).

```sh
curl -sS -X POST "$SIMLOCK_URL/v1/leases/$LEASE/rotate" \
  -H "Authorization: Bearer $SIMLOCK_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"orientation":"landscape_left"}'
```

```json
{"leaseId":"lse_3b9d6c1e-7f2a-4c55-9e0b-8a41d2f6c7e3","orientation":"landscape_left"}
```

`orientation` is `portrait`, `portrait_upside_down`, `landscape_left` or `landscape_right`. The `200` answer means the rotation was sent to the simulator. Through a gateway, use the lease id the gateway gave you. From the JS client, call `client.rotate(leaseId, orientation)`. From the command line, run `simlock rotate landscape-left` (see the [CLI reference](/simlock/docs/reference/cli)).

| Answer | Why |
| --- | --- |
| `400 BAD_REQUEST` | Any other `orientation` spelling. |
| `403` | The lease isn't yours. |
| `404 UNKNOWN_LEASE` | The lease doesn't exist. |
| `422 ROTATION_UNSUPPORTED` | The lease isn't on an iPhone or iPad simulator: an Apple TV, Apple Watch or Apple Vision simulator, an Android device, or a physical iPhone or iPad. |
| `503 INPUT_UNAVAILABLE` | The rotation couldn't be sent to the simulator. |
| `504 EXEC_TIMEOUT` | Through a gateway, the worker didn't answer within `gateway.execTimeoutMs`. |
