An agent on another machine leases and uses devices through Simlock's HTTP API, with an agent token. The same calls work against a single worker and against a gateway.

Most `simlock` commands only talk to the daemon on their own machine, so they can't do this for you. The exception is [`simlock tunnel`](#tunnels).

## Before you start

On the machine you connect to:

- **A standalone worker** has HTTP on by default, on `127.0.0.1:4701`.
- **A worker that has joined a gateway** has HTTP off, and you can't turn it on. Connect to the gateway instead.
- **A gateway** has HTTP on by default, on `127.0.0.1:4700`.

Both only accept connections from the machine itself until you change `http.host`. Simlock doesn't serve HTTPS: put a reverse proxy with TLS in front of it before you open it to a network (see [Configuration reference](/simlock/docs/reference/configuration)).

## Get an agent token

On the worker, or on the gateway for a fleet, create one token per agent:

```sh
simlock token create --role agent --label ci-runner-3
```

```json
{"secret":"slk_d2FybS1wb29sLWFnZW50LXRva2VuLWV4YW1wbGUtMDM","token":{"id":"tok_9f2c71e4-5a3b-4c8d-b1e6-0d7a2f4c9e15","role":"agent","label":"ci-runner-3","createdAt":1792834812000}}
```

The secret is shown only once. Every request sends it as `Authorization: Bearer <secret>`.

- **The token is the requester.** Its leases belong to it, and by default it can hold one lease at a time. An operator can raise that with `lease.maxPerRequester`, overall or per platform. Agents that share a token share that limit.
- **A token only works on the daemon that created it.** A gateway's tokens don't work on its workers.

<Aside type="danger">
An agent token reaches the whole worker, not only one device. A command run through `exec` runs on the worker as the daemon's user, and can read and write files anywhere that user can. For example, `adb pull` writes a file to any path you choose on the worker. Through a gateway, the command runs on whichever worker holds the device. Give agent tokens only to agents you would let run commands on those machines.
</Aside>

## Lease a device

The examples use `curl` and `jq`, with these variables:

```sh
export SIMLOCK_URL=https://simlock.example.com
export SIMLOCK_TOKEN=slk_d2FybS1wb29sLWFnZW50LXRva2VuLWV4YW1wbGUtMDM
```

<Steps>

1. **Ask for a device.** The body takes the same choices as `simlock lease`: `platform` (required), `device` or `class`, `os`, `mode`, `except`, `imageTag`, `physical`, `ttlMs`, `timeoutMs`, `noWait` and `allowDownload`. See [Choosing a device](/simlock/docs/using-devices/choosing-a-device).

   ```sh
   curl -sS -X POST "$SIMLOCK_URL/v1/lease-requests" \
     -H "Authorization: Bearer $SIMLOCK_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"platform":"ios","device":"iPhone 16","ttlMs":1800000}'
   ```

   The answer is `201` with a request, not a device yet:

   ```json
   {"request":{"createdAt":"2026-10-21T09:12:00.000Z","id":"req_7d1a0c4e-2b9f-4e63-8a15-c3f0d6b8e241","state":"queued","queuePosition":2}}
   ```

   When a device is free at once, `state` is already `granted`. A request Simlock can refuse straight away fails here with an error status instead (see [When something goes wrong](#when-something-goes-wrong)).

2. **Wait for the device.** Read the request with `?wait=60`. The call returns as soon as the state changes, or after 60 seconds (the longest you can wait). Repeat it until `state` is `granted`, `failed` or `cancelled`:

   ```sh
   REQ=req_7d1a0c4e-2b9f-4e63-8a15-c3f0d6b8e241
   while :; do
     BODY=$(curl -sS "$SIMLOCK_URL/v1/lease-requests/$REQ?wait=60" \
       -H "Authorization: Bearer $SIMLOCK_TOKEN")
     case $(echo "$BODY" | jq -r .request.state) in
       granted|failed|cancelled) break ;;
     esac
   done
   echo "$BODY"
   ```

   While it waits, `state` is `queued` (with `queuePosition`), `downloading`, `reclaiming`, `provisioning` or `booting` (with `etaSeconds`). A granted request carries the lease:

   ```json
   {"request":{"createdAt":"2026-10-21T09:12:00.000Z","id":"req_7d1a0c4e-2b9f-4e63-8a15-c3f0d6b8e241","state":"granted","lease":{"id":"lse_3b9d6c1e-7f2a-4c55-9e0b-8a41d2f6c7e3","requestId":"req_7d1a0c4e-2b9f-4e63-8a15-c3f0d6b8e241","platform":"ios","device":"iPhone 16","os":"18.6","udid":"6F1D2A8C-3B4E-4F7A-9C2D-8E5B1A7F3C90","address":"6F1D2A8C-3B4E-4F7A-9C2D-8E5B1A7F3C90","deviceId":"dev_8c1f2e7a-4b6d-4e0f-9a3c-5d2b7e1f0a64","createdAt":"2026-10-21T09:12:41.000Z","expiresAt":"2026-10-21T09:42:41.000Z","ttlMs":1800000,"dataPlane":null,"mode":"full"}}}
   ```

   A failed request carries `error` with a `code` and `message`, such as `QUEUE_TIMEOUT` when `timeoutMs` ran out.

   To follow progress as a stream instead, open `GET /v1/lease-requests/<id>/events`. It sends one Server-Sent Event per state change, and ends with `granted` or `failed`.

3. **Keep the lease alive.** Renew before `expiresAt`. Renewing every third of the TTL leaves room for a failed attempt:

   ```sh
   LEASE=lse_3b9d6c1e-7f2a-4c55-9e0b-8a41d2f6c7e3
   curl -sS -X POST "$SIMLOCK_URL/v1/leases/$LEASE/renew" \
     -H "Authorization: Bearer $SIMLOCK_TOKEN"
   ```

   ```json
   {"expiresAt":"2026-10-21T09:52:10.000Z","leaseId":"lse_3b9d6c1e-7f2a-4c55-9e0b-8a41d2f6c7e3","notices":[]}
   ```

   - A renew moves the deadline to now plus the lease's TTL. To change the TTL, send `{"ttlMs": 3600000}` as the body, with `Content-Type: application/json`.
   - `notices` lists device problems since the last renew, such as `{"event":"device_unhealthy"}` and `{"event":"device_recovered","attempts":1}`.
   - Losing your connection does nothing to the lease. A lease nobody renews expires at `expiresAt`, and the device is deleted (a physical device is cleaned).
   - Renewing a lease that has ended answers `404 UNKNOWN_LEASE`. Request a new one.

4. **Run commands on the device.** `exec` runs one `simctl` or `adb` command (or `devicectl` on a physical iPhone or iPad) on the machine that holds the device, and streams the output back. Leave the device out; Simlock adds it:

   ```sh
   curl -sS -N -X POST "$SIMLOCK_URL/v1/leases/$LEASE/exec" \
     -H "Authorization: Bearer $SIMLOCK_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"tool":"simctl","args":["launch","com.example.myapp"]}'
   ```

   ```text
   event: output
   data: {"stream":"stdout","chunk":"com.example.myapp: 48213\n"}

   event: exit
   data: {"exitCode":0}
   ```

   Read [Running commands with exec](#running-commands-with-exec) before you rely on it.

5. **Release the device** when you are done:

   ```sh
   curl -sS -X DELETE "$SIMLOCK_URL/v1/leases/$LEASE" \
     -H "Authorization: Bearer $SIMLOCK_TOKEN"
   ```

   ```json
   {"device":{"id":"dev_8c1f2e7a-4b6d-4e0f-9a3c-5d2b7e1f0a64","state":"reclaiming"},"released":true}
   ```

   The answer is `202`. Simlock then deletes the device in the background (a physical device is wiped instead).

</Steps>

## Running commands with exec

The command runs on the worker, as the user who runs the worker's daemon. Treat an agent token like shell access to the worker: `simctl spawn` and similar commands start programs there. Agents that must not see each other's work belong on separate workers.

- **Leave the device out.** Simlock adds the lease's device to the command: the UDID for `simctl` (where the subcommand takes one), `-s <serial>` for `adb`, and `--device <UDID>` for `devicectl`. Write `["install","/builds/MyApp.app"]`, not a UDID or serial.
- **Naming another device is refused.** A command that names a different device, such as `booted`, another UDID, `adb -s emulator-5556`, `-e`, `-d` or `-t`, is refused with `422 PASSTHROUGH_REFUSED` before anything runs. Naming the lease's own device is accepted, except on a physical Android phone, which refuses any option before the subcommand, even its own `-s <serial>`.
- **Paths are on the worker.** `{"tool":"simctl","args":["install","/builds/MyApp.app"]}` needs `/builds/MyApp.app` to exist on the worker. Upload a file to the lease's folder with [lease files](#lease-files), or use [agent-device](/simlock/docs/using-devices/agent-device), which uploads apps for you.
- **No terminal.** `stdin` in the body is sent to the command once, and may hold at most 8,388,608 characters; a longer one is refused with `BAD_REQUEST`. Interactive commands, such as a bare `adb shell`, are refused.
- **Output is text.** Output is decoded as UTF-8, so binary output, such as a screenshot written to stdout, gets corrupted. Write it to a file on the worker instead.
- **Time limit.** A command that runs longer than 10 minutes is stopped, and the stream ends with an `error` event carrying `EXEC_TIMEOUT`. Disconnecting doesn't stop the command.
- **The same commands are refused as locally.** Everything `simlock simctl` and `simlock adb` refuse (see [Commands Simlock refuses](/simlock/docs/using-devices/working-with-a-device#commands-simlock-refuses)) is refused here with `422 PASSTHROUGH_REFUSED`, before anything runs. So is `simctl` on an Android lease, and `adb` on an iOS one.
- **The command gets a short list of environment variables**: `PATH`, `HOME`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL`, `LANG`, every `LC_*` variable, `TERM`, `DEVELOPER_DIR`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `ANDROID_USER_HOME`, `ANDROID_AVD_HOME`, `ANDROID_PREFS_ROOT`, `ANDROID_SDK_HOME` and `JAVA_HOME`, plus what it needs to reach the device. Other variables, such as a token the daemon was started with, aren't passed. That doesn't make them secret: the command runs as the same user and can read the daemon's environment.

## Lease files

A lease holder (or an operator) can put files into its lease's folder on the worker and read them back, with raw bytes in the request body and no base64. Nothing is held in memory: the body streams to disk, and the file appears under its name once the whole body has arrived. The same calls work against a worker and against a gateway, which relays each one to the lease's worker; `$SIMLOCK_URL` is either.

```bash
curl -X PUT "$SIMLOCK_URL/v1/leases/$LEASE/files/fixture.tar" -H "Authorization: Bearer $T" --data-binary @fixture.tar
# {"name":"fixture.tar","size":70000000}   (201)

curl "$SIMLOCK_URL/v1/leases/$LEASE/files/fixture.tar" -H "Range: bytes=0-99" -H "Authorization: Bearer $T" -o head.bin
# 206, Content-Range: bytes 0-99/70000000, 100 bytes

curl "$SIMLOCK_URL/v1/leases/$LEASE/files" -H "Authorization: Bearer $T"
# {"files":[{"name":"fixture.tar","size":70000000}]}

curl -X DELETE "$SIMLOCK_URL/v1/leases/$LEASE/files/fixture.tar" -H "Authorization: Bearer $T"
# 204
```

- **Names.** 1 to 128 letters, digits, `.`, `_` or `-`, starting with a letter or digit, so `.hidden`, `-rf` and `my file.tar` are refused with `400 BAD_REQUEST`. Names match ignoring case: `A.tar` and `a.tar` are one file, and a `PUT` replaces it.
- **Limits.** 2 GiB a file and 4 GiB a lease folder (files a command wrote there count). A larger file is refused with `413 FILE_TOO_LARGE`, a full folder with `413 LEASE_FILES_FULL`, and nothing is stored when the worker's free disk is under its `diskPressure.freeBytesThreshold` (`422 INSUFFICIENT_DISK_SPACE`).
- **One upload per name.** A second `PUT` to a name being uploaded gets `409 FILE_BUSY`. A `PUT` that is cut leaves the previous file untouched.
- **No total time limit.** An upload is cut only when no byte of its body arrives for 330 seconds (`408 UPLOAD_STALLED`), also through a gateway. Through a gateway, a `Content-Length` over 2 GiB is refused at the gateway, and a worker that is not connected answers `503 WORKER_UNREACHABLE`.
- **Downloads.** `GET` answers the whole file or one `Range` (`bytes=a-b`, `a-` or `-n`) as `206`; a start past the end is `416`. An unknown name is `404 UNKNOWN_FILE`.
- **The folder goes with the lease.** The files are deleted when the lease ends.

## More calls

| Call | What it does |
| --- | --- |
| `DELETE /v1/lease-requests/<id>` | Cancel a request that is still waiting. `204` on success. Once Simlock has started on the device, or granted it, the answer is `409 REQUEST_NOT_CANCELLABLE`: release the lease instead. |
| `GET /v1/leases/<id>` | Read the lease again, for example after your agent restarts. `expiresAt` is the current deadline. |
| `GET /v1/leases/<id>/events` | Server-Sent Events for `device_unhealthy`, `device_recovered` and `lease_lost`. The stream ends after `lease_lost`. |
| `GET /v1/leases` | Your leases. Through a gateway, each one also carries `workerLeaseId`, the id its worker knows it by. |
| `GET /v1/status` | The devices, capacity and queue. With an agent token, `leases` and `waiting` show only your own. To find enrolled phones, see [Physical devices](/simlock/docs/using-devices/physical-devices#see-which-devices-are-enrolled). |
| `GET /v1/catalog?platform=ios` | The models and OS versions you can ask for, as `simlock catalog --json` prints them. |
| `GET /v1/identity` | Who the token is. |

### Send a lease request safely twice

Add an `Idempotency-Key` header (1 to 200 characters) to `POST /v1/lease-requests` to make retries safe. Sending the same key again returns the stored request instead of queueing a second one, until 10 minutes after the request finished.

### Caching

- A `GET` under `/v1` that answers `200` with JSON carries an `ETag` header. Send it back as `If-None-Match` on the next read of the same route: while nothing changed, the answer is `304 Not Modified` with no body. Event streams carry no `ETag`.
- Simlock's own JSON answers under `/v1` (errors, `304` and `/v1/healthz` included) carry `Cache-Control: no-store`, so a CDN or proxy cache in front of Simlock never stores them. Other routes, such as the device stream, set their own `Cache-Control`.

## Through a gateway

Send the same calls to the gateway, with a token created on the gateway. The gateway picks a worker for you.

- **A lease id from a gateway names its worker**, such as `3f81a2c4-9b7d-4e21-8a55-1c0e6f2d7b93.lse_9f2c6a1d`. Pass it back exactly as you got it. The lease also carries `worker`, with the worker's id and label.
- **`allowDownload` downloads nothing.** Only OS versions already installed on a worker count.
- **A request no worker can serve fails at once**, with or without `noWait`.
- **When the worker that holds your lease isn't connected**, calls for it answer `503 WORKER_UNREACHABLE`. The lease is still yours until it expires, so retry.

## Tunnels

A tunnel connects ports between your machine and a leased Android device or iOS simulator on another machine:

- **`reverse`** lets the device reach a server on your machine, such as Metro.
- **`forward`** lets your machine reach a port on the device.

iOS simulators take tunnels; an iPhone does not. A simulator has no network of its own: an app in it listens on the worker's loopback and reaches the worker's ports. So `reverse 8081` makes the worker listen on port 8081 itself, on `127.0.0.1` and `::1`, and two leases on one worker cannot reverse the same port. `reverse` is refused with `TUNNEL_PORT_IN_USE` when anything on the worker already listens on that port. `forward 9100` reaches port 9100 only when a process of your own lease's simulator listens there; a port that another simulator's app, the worker's own tools or nothing listens on is closed, and `simlock tunnel` prints the reason on stderr.

An Android emulator also takes the **`emulator adb`** tunnel: your own `adb`, and so Android Studio, lists the remote emulator as a device and drives it.

### Before you start

Tunnels are off by default. Turn on `capabilities.tunnel.enabled` on the worker, and on the gateway too if you go through one, then restart each daemon.

### Open a tunnel with `simlock tunnel`

`simlock tunnel` talks to the worker or gateway over HTTP, so it doesn't need a daemon on your machine:

```sh
export SIMLOCK_URL=https://simlock.example.com
export SIMLOCK_TOKEN=slk_d2FybS1wb29sLWFnZW50LXRva2VuLWV4YW1wbGUtMDM
simlock tunnel reverse 8081
```

```text
reverse device:8081 -> localhost:8081 (lease lse_3b9d6c1e-7f2a-4c55-9e0b-8a41d2f6c7e3)
```

Now an app on the device that connects to `localhost:8081` reaches port 8081 on your machine. The tunnel stays open until you press Ctrl-C.

- With an agent token that holds one lease, the command finds the lease for you. Otherwise pass `--lease <lease-id>`.
- `reverse 8081:9000` connects the device's port 8081 to port 9000 on your machine.
- Device ports must be 1024 or higher. You can open up to 8 tunnels per lease.
- When the lease ends, the command exits with code 14 and `TUNNEL_LEASE_ENDED`.

Every flag and failure is in the [CLI reference](/simlock/docs/reference/cli#simlock-tunnel).

<Aside type="caution">
While a tunnel is open, its port on the worker can be reached by others on that machine: any process on the worker, another lease's emulator (at `10.0.2.2`), and any other lease's device with an `adb reverse` rule to it. Don't send anything through a tunnel you wouldn't show them.
</Aside>

What else to know:

- On an iOS simulator, a reverse port that any process on the worker already listens on is refused with `TUNNEL_PORT_IN_USE`, whichever lease it belongs to.
- A port you already reversed yourself with `adb reverse` through `exec` is refused with `TUNNEL_PORT_IN_USE`. An `adb reverse` rule you set through `exec` after the tunnel opens replaces it, and the tunnel stops working.
- On a phone, Simlock only removes the rules its own tunnels set. It never clears the phone's other `adb reverse` or `adb forward` rules.
- If the worker crashes while a tunnel is open, the tunnel's rule stays on the phone until it reboots or you remove it with `adb reverse --remove`. Until then, that port can't be used for new tunnels.

### Drive a remote emulator with your own adb

```bash
simlock tunnel emulator adb
```

```text
emulator localhost:61544 -> emulator:adb (lease 9c1d)
adb: connected to 127.0.0.1:61544
```

The command runs `adb connect` for you and `adb disconnect` when you press Ctrl-C, so `adb devices` on your machine lists `127.0.0.1:61544` as a `device`. Shell, install, Logcat, the debugger and `adb reverse` work on it. Your adb and Simlock's own adb server on the worker both stay connected to the emulator at once. `emulator adb:6000` picks the caller port yourself.

- The lease must be on an Android emulator. A phone or an iOS simulator is refused with `TUNNEL_UNSUPPORTED`.
- A Play Store image keeps `ro.adb.secure` on, so your adb lists it as `unauthorized` and the command warns `adb answered: failed to authenticate`. Lease a `google_apis` image instead.
- If the command cannot find or run your adb, it warns and keeps the tunnel open; run the `adb connect` it prints.
- Rules you add with `adb reverse` live on the emulator and go when the lease ends. A rule on a device port you later pass to `simlock tunnel reverse` makes that tunnel fail with `TUNNEL_PORT_IN_USE`.

### Build your own tunnel client

`simlock tunnel` covers most needs. If you write your own client, open `GET /v1/leases/<lease-id>/tunnel` as a WebSocket with your token, on the worker or the gateway.

**Who can open it.** The lease's holder and an operator. Anyone else gets `404`, as for an unknown lease. A plain `GET` without an upgrade gets `426`.

**Frames.** Each message is one binary frame: a tag byte, a 4-byte big-endian connection number, and a payload. A frame can be at most 65541 bytes; a longer one is refused with `BAD_REQUEST`, and the socket closes with 4003.

| Tag | Name | Sent by | Payload |
| --- | --- | --- | --- |
| `0x01` | `HELLO` | You, first, on connection 0 | JSON of at most 4 KiB, such as `{"tunnels":[{"kind":"reverse","devicePort":5173}]}` |
| `0x81` | `READY` | Worker | The same list of tunnels |
| `0x82` | `REFUSED` | Worker | JSON `{code, message}`; the socket then closes with 4003 |
| `0x02` | `OPEN` | Both | JSON `{kind, devicePort}`: a new connection |
| `0x03` | `DATA` | Both | Up to 65536 bytes |
| `0x04` | `CREDIT` | Both | A 4-byte count: how many more bytes the reader accepts |
| `0x05` | `END` | Both | Closes one direction; the other stays open |
| `0x06` | `RESET` | Both | Closes the connection; from the worker, JSON `{reason}` |

**Setting up.** `HELLO` names 1 to 8 tunnels per lease, across all its sockets, each `reverse` or `forward`, with device ports from 1024 to 65535, or `{"kind":"emulator","emulatorPort":"adb"}` for an Android emulator's adb port (any other `emulatorPort` is `BAD_REQUEST`; a lease that is not on an emulator is refused `TUNNEL_UNSUPPORTED`). A `HELLO` the worker can't meet gets `REFUSED`, and nothing it named stays set up. The codes are in the [errors reference](/simlock/docs/reference/errors#tunnels). A frame that breaks the protocol is refused with `BAD_REQUEST` the same way.

**Reverse connections.** Each connection the device makes to `localhost:<devicePort>` arrives as `OPEN`, with an odd connection number. Its bytes then flow as `DATA` both ways.

**Forward connections.** You open them: send `OPEN` with an even connection number above your last one, and JSON `{"kind":"forward","devicePort":<port>}` naming a `forward` tunnel of this socket, then send `DATA` at once. The worker answers `RESET` when nothing listens on the device port (on an iOS simulator: when no process of the lease's simulator does), when the device doesn't answer within 5 seconds (reason `timeout`), or when 256 connections are already open on the socket (reason `too many connections`). An `OPEN` that breaks these rules is refused with `BAD_REQUEST`.

**Emulator connections.** Like forward connections, you open them with `OPEN` and JSON `{"kind":"emulator","emulatorPort":"adb"}`, for an `emulator` tunnel of this socket. The worker connects to the emulator's adb port, and answers `RESET` when nothing listens there or the emulator does not answer within 5 seconds (reason `timeout`).

**Flow control.** Each direction of a connection starts with a 262144-byte window. The reader grants more with `CREDIT`. A reader that grants none pauses that one connection and no other.

**Limits.** At most 256 connections per socket, counting yours and the device's together. A device connection beyond that is closed at once.

**When the socket closes:**

| Code | When |
| --- | --- |
| 4001 | The lease ended. The reason is the lease-end reason. |
| 1001 | The daemon stopped, or through a gateway, the gateway stopped. |
| 1011 | Through a gateway, the lease's worker stopped or stopped answering. |

Before the upgrade, a worker with tunnels off answers `503 TUNNEL_UNAVAILABLE`, and one that doesn't answer within 10 seconds answers `503 WORKER_UNREACHABLE`. Closing the socket removes the device's tunnel rules before the lease can end.

## When something goes wrong

Errors come back as JSON with an HTTP status:

```json
{"error":{"code":"REQUESTER_ALREADY_LEASED","message":"Requester tok_9f2c71e4-5a3b-4c8d-b1e6-0d7a2f4c9e15 already holds lease lse_3b9d6c1e-7f2a-4c55-9e0b-8a41d2f6c7e3; release it (`simlock release lse_3b9d6c1e-7f2a-4c55-9e0b-8a41d2f6c7e3`) before requesting another device"}}
```

| Status | Code | What to do |
| --- | --- | --- |
| `400` | `BAD_REQUEST` | Fix the body: for example, it names both `device` and `class`, or a `ttlMs` above the maximum. A body that isn't valid JSON gets the message `Invalid JSON body`. |
| `401` | `UNAUTHENTICATED` | The token is missing or unknown. Check the `Authorization` header. |
| `403` | `FORBIDDEN` | The lease or request belongs to another token, or the route needs an operator token. |
| `404` | `UNKNOWN_LEASE` | The lease has ended or never existed. Request a new one. |
| `409` | `REQUESTER_ALREADY_LEASED` | This token already holds or waits for as many leases as it may, or, with a limit per platform, has a request waiting on that platform. Release or cancel it first. |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | A request with a body didn't send `Content-Type: application/json`. |
| `422` | `UNKNOWN_MODEL`, `RUNTIME_MISSING`, `NO_DRIVER` | The device you asked for can't be made on this machine or fleet. Check `GET /v1/catalog`. |
| `503` | `NO_CAPACITY` | Nothing is free and you sent `noWait: true`. Try again after the `Retry-After` seconds. |

See [Errors](/simlock/docs/using-devices/errors) for what each code means.
