[agent-device](https://github.com/callstack/agent-device) is Callstack's command-line tool for driving mobile apps: it opens an app, reads the screen as a tree of elements, taps, types and takes screenshots.

With Simlock, `agent-device open` leases a device from Simlock, and every later command goes to that device. Each agent gets its own device, and the device is deleted when the agent closes it.

```sh
agent-device open --platform ios --device "iPhone 16"
agent-device snapshot
agent-device close
```

## Before you start

On each worker:

- agent-device 0.21.28 or later, installed so the user who runs the Simlock daemon can run `agent-device`. Simlock never installs or updates it.
- HTTP on, because agents reach agent-device over HTTP. A standalone worker has it on by default.

On each agent's machine:

- agent-device 0.21.28 or later. An older one is refused with `refused: this agent-device is too old for simlock; upgrade it`.
- Its own Simlock agent token, unless the agent runs on the worker's Mac (see [On the same Mac](#on-the-same-mac)).

<Aside type="caution">
Simlock tells agents apart by token. Two agents that share a token share one agent-device session and see each other's devices.
</Aside>

## Turn it on

<Steps>

1. **On a standalone worker**, agent-device is on by default, with HTTP on `127.0.0.1:4701`. Install agent-device, then restart the worker so it finds the command:

   ```sh
   simlock daemon stop
   simlock daemon start
   ```

   Until agent-device is installed, the worker shows agent-device as `off`, and `simlock doctor` doesn't mention it.

   **On a worker that has joined a gateway**, agent-device is off (and HTTP is always off). Turn agent-device on:

   ```sh
   simlock config set capabilities.agent-device.enabled true
   ```

   Once you set it to `true` yourself, a missing `agent-device` command shows up in `simlock doctor`. If `agent-device` isn't on the daemon's `PATH`, set `capabilities.agent-device.command` to its full path.

   For agents on other machines, set `http.host` and put a reverse proxy with TLS in front. Simlock doesn't serve HTTPS itself (see [Configuration reference](/simlock/docs/reference/configuration)).

2. **With a gateway**, turn agent-device on there too. The gateway sends each agent to a worker where agent-device works:

   ```sh
   simlock --gateway config set capabilities.agent-device.enabled true
   ```

3. **Restart each daemon you changed:**

   ```sh
   simlock daemon stop
   simlock daemon start
   ```

4. **Check it.** `simlock worker list` ends each worker's line with `agent-device available`, `agent-device off`, or `agent-device unavailable:` and the reason. `simlock doctor` reports the same problem and how to fix it:

   ```text
   agent-device  fail  found 0.20.3, need 0.21.28 or later; install agent-device 0.21.28 or later, then restart the daemon (`simlock daemon stop`, then `simlock daemon start`)
   ```

5. **Create one agent token per agent**, on the worker, or on the gateway for a fleet:

   ```sh
   simlock token create --role agent --label ui-agent-1
   ```

   ```json
   {"secret":"slk_Qm9yZWFsaXMtNzEzMi1kZXZpY2UtdG9rZW4tZXhhbXBsZQ","token":{"id":"tok_5e0a9c3d-2f7b-4d1e-8c6a-3b9f1e7d2a50","role":"agent","label":"ui-agent-1","createdAt":1792834812000}}
   ```

   The secret is shown only once. Give it to the agent.

</Steps>

If agent-device is missing or too old, Simlock keeps running without it, and every agent-device request answers `agent-device is not available on this simlock:` with the reason. After you fix it, restart the daemon.

## Drive an app

On the agent's machine, connect agent-device to Simlock once, then use it as usual:

```sh
export AGENT_DEVICE_DAEMON_AUTH_TOKEN=slk_Qm9yZWFsaXMtNzEzMi1kZXZpY2UtdG9rZW4tZXhhbXBsZQ
agent-device connect proxy --daemon-base-url https://mac-studio-2.example.com/v1/agent-device
export AGENT_DEVICE_SESSION=agent-1

agent-device open --platform ios --device "iPhone 16"
agent-device install MyApp ./build/Debug-iphonesimulator/MyApp.app
agent-device open com.example.myapp
agent-device snapshot
agent-device screenshot home.png
agent-device close
```

The URL is the worker's HTTP address, or the gateway's (port 4700 by default), followed by `/v1/agent-device`.

<Aside type="caution" title="Several agents on one machine">
Each agent sets its own `AGENT_DEVICE_SESSION` (or passes `--session` on every command). Without one, a command uses the last session saved on that machine, which may be another agent's. It then fails with `No active proxy device lease for this session; run open first.` or `refused: lease <id> is not one of yours on this gateway`.
</Aside>

Each agent-device session holds one device. To use a second device, open a second session.

### Ask for a device with `open`

`open` takes a lease. `--platform ios` or `android` is required. With nothing else, you get a phone.

- `--device "iPhone 16"` asks for that model.
- `--target mobile`, `tv` or `desktop` asks for a phone, a TV or a desktop device.
- `--os` names an OS version or a range: `26.0`, `>=18 <27`, `18 - 26`. A range gets the newest installed version inside it.
- On Android, `--image-tag` names a system image tag, such as `google_apis_playstore`.
- `--physical` leases an enrolled phone (see [Use a real phone](#use-a-real-phone)).
- On the `agent_device.lease.allocate` request, `deviceMode: "full"` or `"slim"` asks for that kind of iOS simulator. Without it, you get the worker's default. agent-device 0.21.36 has no CLI flag for it.

The reply to `open` names the model, OS and image tag you got. If every matching device is taken, `open` waits for up to 330 seconds, then fails with `timed out waiting for a device; nothing was leased`.

### What to expect

- **The lease is an ordinary Simlock lease.** `simlock status` and the console show it, held by your token. Its id is the one agent-device chose.
- **Commands keep the lease alive.** An agent that stops sending commands loses the device one TTL later. The TTL is the one agent-device asks for, or the worker's default (15 minutes). An admin can cap it with `capabilities.agent-device.leaseTtlCapMs`.
- **`close` gives the device back.** Simlock ends the lease and deletes the device. The next agent gets a new one.
- **`install` sends the app from your machine.** The path is on the agent's machine, and agent-device uploads the app. A path on the worker is refused with `refused: send the app from your machine as an upload`.
- **`devices` lists only your devices**, and nothing before `open`.
- **A `batch` can nest at most 8 levels deep and hold at most 1000 steps in all.** A larger one is refused before any step runs, with `refused: a batch nests more than 8 levels deep` or `refused: a batch has more than 1000 steps`.
- **`orientation` on an iPhone or iPad simulator is done by Simlock.** `agent-device orientation landscape-left` replies `Rotation requested: landscape-left (unconfirmed)`: the rotation was sent, but nothing confirms it happened. You can use `portrait`, `portrait-upside-down`, `landscape-left` and `landscape-right`, or the short forms `upside-down`, `left` and `right`. Anything else, `auto` included, is refused with `Unknown orientation <name>; use portrait, portrait-upside-down, landscape-left or landscape-right`. If Simlock can't send it, the command fails with Simlock's `INPUT_UNAVAILABLE` message. On other devices (Android, a physical iPhone or iPad, an Apple TV simulator), and as a step of a `batch`, agent-device rotates as it normally does.

## On the same Mac

An agent on the worker's own Mac, running as the same user, doesn't need a token of its own. This works on a standalone worker, where HTTP and agent-device are on by default.

Each time the worker starts, it writes `agent-device-profile.json` in its data folder (`~/.simlock/` for a user session), readable only by that user. Connect with that file:

```sh
agent-device connect --remote-config ~/.simlock/agent-device-profile.json --session s1
agent-device open --platform ios --session s1
agent-device snapshot --session s1
agent-device close --session s1
```

Pass `--session` on every command. All local agents share the file's one token, so give each agent its own `--session` name, or they will see each other's devices.

What to know about the file:

- The worker keeps the same token across restarts, so a saved connection keeps working.
- If the file changes anyway (you changed `http.port`, or revoked the token with `simlock token revoke`), agent-device refuses the saved connection with `Active remote connection config changed`. Refresh it with `agent-device connect --remote-config ~/.simlock/agent-device-profile.json --session s1 --force`.
- The worker removes the file, and revokes its token, when you turn HTTP or agent-device off (`http.enabled` or `capabilities.agent-device.enabled` set to `false`).
- A worker that has joined a gateway doesn't write the file.
- The file's token is labelled `agent-device on this Mac`. Don't give your own tokens that label: the worker revokes them at its next start.

## Use a real phone

agent-device can drive phones enrolled in Simlock (see [Physical devices](/simlock/docs/using-devices/physical-devices)). `open --physical` leases one, and the reply names the device with `physical: true`. Simlock picks the phone, so don't pass `--udid` or `--serial`.

Phones need extra setup on the worker:

- **For an iPhone**, set the signing team and bundle id, then restart the daemon:

  ```sh
  simlock config set capabilities.agent-device.ios.teamId <team-id>
  simlock config set capabilities.agent-device.ios.bundleId <bundle-id>
  ```

  `provisioningProfile` and `signingIdentity` are only for manual signing. Setting a provisioning profile switches agent-device to manual signing, which fails with an Xcode-managed profile.

- **For an Android phone**, the worker's phone support uses `adb` without Simlock's version check. Make sure it comes from the same Android SDK platform-tools as Simlock's.

If phone support can't start, `simlock doctor` prints a line starting `phone daemon:`, and phone requests answer `agent-device is not available on this simlock: phone daemon: <message>`. Simulators and emulators keep working.

## Through a gateway

Point `connect proxy` at the gateway, and use a token created on the gateway. `open` lands on a worker where agent-device works, and every later command for that device goes to the same worker. You never name a worker.

If that worker disconnects, requests for your device answer `agent-device is not available on this simlock: the worker holding this device is not connected to the gateway; try again`. Nothing is released. Once the worker is back, and before the lease runs out, the next request works on the same device.

## When Simlock ends the lease

If the lease ends for any reason other than your `close` (it expired, an admin released it, the device was lost, or the worker's daemon or agent-device restarted), the next command answers:

```text
lease ended by simlock; run disconnect, then open
```

Run `agent-device disconnect`, then `open` again. You get a new, clean device; anything on the old one is gone.

<Aside type="caution">
Restarting a worker's daemon ends every agent-device lease on that worker, even though ordinary Simlock leases survive a restart.
</Aside>

## Messages you may see

| Message | Meaning |
| --- | --- |
| `refused: agent-device through simlock needs an agent token` | You used an operator token. Create an agent token. |
| `refused: name --platform ios or android` | `open` needs `--platform`. |
| `refused: simlock picks the device` | A `--udid`, `--serial` or `--device` names a device that isn't the one Simlock leased to you. |
| `refused: simlock chooses the device set; run disconnect, then connect proxy without --ios-simulator-device-set` | Simlock decides which devices agent-device sees. |
| `No active proxy device lease for this session; run open first.` | The session has no lease, often because parallel agents on one machine share a session. Set `AGENT_DEVICE_SESSION` (or pass `--session`) per agent, then `open`. |
| `refused: lease <id> is not one of yours on this gateway` | The command named another session's or token's lease, often for the same reason. Give each agent its own `AGENT_DEVICE_SESSION`, then `open` again. |
| `refused: malformed physical` | `physical` wasn't true or false. |
| `refused: unknown --target <value>; use mobile, tv or desktop` | `--target` named a kind of device Simlock doesn't know. |
| `refused: malformed osVersion`, `refused: malformed imageTag` | `--os` or `--image-tag` wasn't text. |
| `refused by simlock: <message>` | Simlock refused the lease, for example for a model it doesn't know, an OS range it can't read, an image tag on iOS, or a `deviceMode` other than `slim` or `full` (`null` means absent). |
| `refused: this agent-device is too old to use through a gateway; update it` | Update the agent's agent-device. |
| `agent-device is not available on this simlock: <reason>` | agent-device is missing, too old, starting or crashed on the worker. |
| `agent-device is not available on this simlock: phone daemon: <message>` | Phone support on the worker is starting or down. Simulator leases keep working; `simlock doctor` says what is wrong. |
| `refused by simlock: No worker in the fleet can currently serve this request` | Every worker that can serve agent-device is drained. Undrain a worker, or wait. Leases you already hold keep working. |
